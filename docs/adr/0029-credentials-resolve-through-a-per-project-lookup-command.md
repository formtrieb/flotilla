# Credentials resolve through a per-project lookup command

The ambient-variable doctrine (a `GITHUB_TOKEN` export in the shell profile) breaks twice for an operator running several consumer repos in parallel. Fine-grained PATs are repo-scoped, so one global variable forces either an over-broad classic PAT everywhere (maximum blast radius — this project has rotated tokens twice) or wrong-token failures in every project but one. And as long as the token is an ambient variable, the whole echo/dump/read leak class stays structurally open: seven live occurrences across three vectors, the seventh landing the same day the convention was sharpened to bind every role — the strongest evidence yet that reminders do not close this class. Convention 8's own assessment already named "keep the credential out of the shell environment" as the structural candidate needing an ADR. Decision: the engine resolves credentials lazily through a per-credential **lookup command** configured in the tracked settings env block; the ambient variable remains a first-class path for ephemeral environments, not a deprecated one.

## Decision

- **One resolver seam.** A single engine-owned credential-resolver module, consumed by the tracker-store factories (`github-api-factory`, `linear-api-factory`), the Bitbucket landing-host factory (`bitbucket-api`'s `createBitbucketApiFromEnv`), and the `host-pr` create/preflight edge. Resolution happens at construction time, once per credential per process; nothing is persisted. `credential-discovery-drift.spec.ts` is the authority for the current, complete set of production consumers — it reconciles every resolver call site against the discovery list by symbol identity, so this bullet does not have to be kept exhaustive by hand as adapters are added.
- **The lookup is a command contract, not a vendor integration.** The `<VAR>_CMD` environment variable carries a command string; the engine spawns it via the platform shell (`sh -c` on POSIX), captures stdout (trailing newlines trimmed) as the secret, captures stderr and never re-prints it. The spawn is timeout-bounded (60 s) so a hung GUI prompt fails loud instead of hanging a wave. Failure is a typed error that names the command — never its stdout or stderr.
- **Mechanical naming.** `GITHUB_TOKEN_CMD`, `LINEAR_API_KEY_CMD`, `BITBUCKET_TOKEN_CMD`: whatever ambient variable an adapter reads, `<VAR>_CMD` is its command counterpart. The precedence rule is statable per pair ("`X_CMD` wins over `X`"), and every future store adapter inherits the naming for free — `credential-discovery-drift.spec.ts` reconciles the full, current set of resolved variables against the resolver's own call sites, so this bullet's pairs are illustrative, not a maintained inventory.
- **Precedence: a configured command wins, and fails loud.** Exit ≠ 0 *or* empty stdout is a typed, loud error — never a silent fallback to the ambient variable (silent fallback re-opens the wrong-token class invisibly: you believe you run repo-scoped and actually run over-broad). An empty or whitespace-only `_CMD` value means "not configured", so the ambient path applies — the deliberate per-environment escape hatch (CI on an adopted consumer overrides with `GITHUB_TOKEN_CMD=""`).
- **The channel is the tracked settings env block** (the proxy-flag precedent). It travels with every checkout, including tracked-files-only agent worktrees — the constraint every gitignored-file approach fails — and it carries the command, never the secret. The engine contract stays harness-agnostic (ADR-0009): the engine reads `process.env`; that Claude Code's settings env block sets the variable is a harness detail outside the engine.
- **Two first-class paths, chosen by environment lifetime.** Long-lived interactive machines adopt the indirection (the new wave-setup default); ephemeral environments — CI injects a per-job-scoped token into a minutes-lived environment with no keychain — use the ambient path *by design*. There is no deprecation horizon for the ambient path: its end state would be unreachable, and a deprecation whose end state is unreachable is not one.
- **AFK posture: prompts fire at preflight, never mid-wave by construction.** The two auth preflights (wave-start step 4, wave-close phase 2) probe each configured `_CMD` value-free (exit code only, never output) in the interactive session before dispatch. wave-setup scaffolds the keychain item with the default ACL — `security add-generic-password` trusts the creating `security` binary, so later `find-generic-password` lookups never prompt — and performs one first resolution as a **live-gate**: it proves the wiring end-to-end, and for session-authenticated resolvers (`op`) it is also the auth exercise. It is *not* an "ACL bind" (for the security path there is nothing to bind — the PRD's original mechanism was wrong on this point). Mid-wave session expiry (a locked keychain, an expired `op` session) surfaces as the typed loud error → a row failure, not a hang; resolvers requiring per-invocation confirmation are documented AFK-incompatible.
- **The residual vector is anchored, not just described.** After adoption the environment carries the *pointer*, not the secret — the leak class morphs from "expand the variable" to "execute the lookup". wave-setup therefore also scaffolds a tracked `permissions.deny` entry for the exact lookup-command prefix it scaffolds (agents' Bash tool is blocked; the engine's own `child_process` spawn inside an allowlisted CLI invocation is untouched — no conflict), and Convention 8 gains the clause: never execute the configured lookup command — its stdout *is* the secret; the sanctioned auth check is the engine's value-free preflight probe. Honest scope, per the convention's own doctrine: the deny anchors the direct form; wrapped forms (`echo $(…)`, `sh -c` wrappers) remain the separate PreToolUse-hook candidate's territory — a speed bump owed its own ticket, not this ADR.

## Considered Options

- **Silent fallback when a configured command fails** (rejected) — the strongest argument for it is the CI scenario (tracked `_CMD` travels into a checkout with no keychain but a valid Actions-injected ambient token). It still loses: a silent degradation runs the over-broad token precisely when the operator believes the repo-scoped one is active. The empty-`_CMD` escape hatch serves the CI case explicitly instead.
- **Ambient variable wins over the command** (rejected) — a forgotten global export would permanently override the clean per-project configuration, and the env-dump leak surface stays open on adopted consumers.
- **Role-based naming** (`FLOTILLA_HOST_TOKEN_CMD` / `FLOTILLA_TRACKER_KEY_CMD`) (rejected) — collapses on the github store, where host credential and tracker credential are the same token; it would create a new precedence question instead of answering one.
- **`FLOTILLA_`-prefixed names** (rejected) — breaks the mechanical pairing with the deliberately unprefixed ambient variables (`GITHUB_TOKEN` is the Actions/gh convention); the collision risk of `GITHUB_TOKEN_CMD` is negligible.
- **A gitignored config file as the channel** (rejected) — fails tracked-files-only agent worktrees, the constraint that disqualifies every gitignored approach (the same reason `wave.config.json` cannot carry it).
- **The code-host CLI's credential helper** (rejected) — the CLI left the landing path long ago; the landing seam is raw fetch behind `GitHubApi` (ADR-0019/0023).
- **A restrictive keychain ACL** (rejected) — every mid-wave resolution would prompt, breaking AFK dispatch by construction. The trade-off is named honestly instead: with the default ACL, any local process in the operator's session can read the item via the `security` CLI — the keychain protects the token *at rest* (disk, backups), not against a live local process. The class this design targets is the accidental transcript leak, and six of the seven live occurrences were accidental forms that now have nothing to show.
- **Coordinator resolves once and exports to agent environments** (rejected) — re-opens the entire echo/dump class in exactly the sessions being detoxified.
- **argv whitespace-split spawn, no shell** (rejected) — breaks the quoting real lookup tools need (`op read "op://vault/item/field"`). The trust boundary is unchanged either way: tracked settings already carry `permissions.allow` and hooks, so a malicious command swap via PR is the same accepted class as a malicious allowlist edit.

## Consequences

- Engine: the credential-resolver module plus specs — precedence with and without each source present; the typed failure carrying the command name and never stdout/stderr; the secret never appearing in logs, error messages, or thrown values; both stores and the host adapter resolving through the one module; and the Convention-11 negative control (a deliberately broken command must fail loud — a resolver only observed succeeding is unproven). The `host-pr` posture texts that say "the ambient GITHUB_TOKEN" are updated — after the indirection, "ambient" would be simply false there.
- wave-setup: scaffolds the keychain item, the `_CMD` entry in the tracked settings env block, and the matching `permissions.deny` entry; runs the first-resolution live-gate; the shell-profile-export doctrine is **replaced**, not supplemented — no setup doc says "export globally in your profile" afterwards.
- wave-start step 4 and wave-close phase 2 gain the value-free `_CMD` probe alongside the existing presence check.
- Convention 8: an amendment adds the never-execute-the-lookup clause and states the structural gain as fact — an env dump on an adopted consumer has nothing to show.
- The per-project direnv + keychain setup stays documented as the interim for non-adopters, explicitly marked a half-measure: it solves the wrong-scope half and leaves the secret in the process environment.
- flotilla itself adopts immediately — the first consumer of its own seam, as with every seam before it.

## Amendment 2026-08-14 — the first-read prompt is environment-conditional; the AFK argument runs on the live-gate, not on "never prompts"

Filed against issue #544, which found the AFK-posture bullet above disagreeing with `wave-setup`'s own reference: the bullet says the default-ACL keychain item's later lookups "never prompt," and its neighbouring "not an ACL bind" clause reads that as true of the very *first* lookup too. The reference documents the opposite — a first-value-read prompt, with field evidence (`security find-generic-password -w` exiting 161, empty stdout, twice, before an explicit **Always Allow** click). Rather than picking a side by fiat, this amendment performs the determination the issue asked for.

**Determination (2026-08-14, macOS Darwin 25.5.0).** A throwaway keychain item (`flotilla-544-scratch-probe`, a scratch value, never a real credential) was created, read, and deleted. Creation via the dispatched agent's own sandboxed Bash tool was refused outright — exit 161, `UNIX[Operation not permitted]` — a sandbox-layer denial at the *create* step, orthogonal to the ACL/prompt question this row measures (creation is an operator-only step in this doctrine to begin with; a dispatched Worker never runs it). Re-run outside that sandbox — the operator-terminal security context this doctrine actually describes — creation succeeded silently. The **first** value-read (`security find-generic-password -a … -s flotilla-544-scratch-probe -w`, output redirected to a file, never printed) exited **0** with **28 bytes** on stdout (matching the stored scratch value's length) and empty stderr — no dialog, nothing to click. Three further reads, each necessarily a fresh process (every CLI invocation of `security` is one), under both the dispatched-agent sandbox and outside it, reproduced the identical clean result every time. The scratch item was deleted with `security delete-generic-password` afterward.

**Reading the two data points together.** This determination's clean, promptless first read does not discredit the reference's own recorded observation (exit 161, twice, resolved only by an explicit Always-Allow click) — both are real measurements, on environments this ADR cannot assume are identical. Getting a second, disagreeing measurement is exactly what it takes to eliminate "the reference is simply right (or wrong) unconditionally": **the first-read prompt is conditional**, not a fixed property of the default ACL. This determination did not fully isolate the discriminating variable — a macOS/keychain-implementation version difference is the leading candidate (this determination's Darwin 25.5.0 postdates the reference's own field evidence), and a codesigning/session-trust detail of the reading process is not ruled out either — but the conditionality itself is now established on two independent, contradicting measurements, not asserted from one side's silence.

**What this supersedes.** The AFK-posture bullet's parenthetical above — "for the security path there is nothing to bind" — is retired as a universal claim. On an environment where the first read prompts, the operator's Always-Allow click *is* an access-control decision, exactly the thing that parenthetical denied could happen. On an environment where it does not (this determination's), the parenthetical's narrower claim — nothing to bind — still holds there. Which case a given consumer machine is in is now a live-gate question, not a doctrine assertion.

**The AFK argument, re-based.** The safety property never actually needed "never prompts" — it needs the first-ever resolution of a credential to happen with a human present, before any wave dispatches unattended. The live-gate step (`wave-setup` Procedure step 8, re-running `store-preflight`) already **is** that first resolution, interactively, at setup. Whichever way a consumer's own environment falls — no prompt ever possible, or one prompt absorbed by the operator's own Always-Allow click at setup — the live-gate is what exhausts it, not a structural guarantee about the default ACL that this determination shows does not hold everywhere. Every later, dispatched read — a Worker's, a Reviewer's, `wave-start`'s or `wave-close`'s own preflight — reuses whichever of those two states this machine is actually in; neither state includes a fresh prompt appearing mid-wave. Mid-wave session expiry (a locked keychain, an expired `op` session) remains the loud-typed-error case the original bullet already names, unaffected by this amendment.

**Consequences of this amendment.** `wave-setup`'s SKILL.md Credentials section and its live-gate framing are corrected to state the conditional finding and this re-based argument, replacing their "never prompts by construction" / "not an ACL bind" claims. `reference/setup-mechanics.md` keeps its own field evidence as a real, dated observation, now stated as one of two possible outcomes rather than the universal one — with a pointer here for the fuller, environment-conditional picture.
