# Linear claims live in workflow states; the triage vocabulary stays in labels

The M2-pulled-forward **`LinearIssuesStore`** maps flotilla's two-scope state onto Linear as follows: the **claim ledger** (`queued → in-flight → in-review`) is written as the issue's **native workflow state** (config-mapped, defaults `Todo / In Progress / In Review`; `done` derives from state *type* `completed` **or** `canceled`/`duplicate` — the same lossy collapse as ADR-0002's GitHub `not_planned`→`done`, `not_planned` being GitHub's issue `state_reason` rather than any Linear token; `unclaim` moves back to `Backlog`). Everything vocabulary-shaped stays a **label**, exactly like the GitHub adapter: the Eligibility OR-set (`ready-for-agent`), the triage vocabulary, `risk/*`/`worker/*`, and the orthogonal `wave/needs-attention` flag (ADR-0006 — a flag *cannot* be a state). `files`/`blockedBy`/`AC` go to the issue body via the **same body-codec** (lifted out of `adapters/github/` to a shared home — it was always markdown-in-body, not GitHub). The store's identity (ADR-0001) is the human team key (`DES-16`); the Linear UUID stays seam-internal. The adapter sits behind a **`LinearApi`** domain seam + in-memory fake (P3 pattern) and must pass the cross-store conformance suite **with zero changes**; the real impl is raw-`fetch` GraphQL behind a **`LinearHttp`** seam (`LINEAR_API_KEY` env, `createLinearApiFromEnv` at the CLI edge — ADR-0019 parity, simpler because Linear has no REST branch).

## Why

- **The board is the point.** ADR-0002's coarse ledger exists so *humans and concurrent fleets see what is claimed*. On GitHub the only projection surface was labels; on Linear the workflow state **is** the surface humans watch — a label-based ledger would leave the board static while agents work, surrendering exactly the visibility the ledger is for. Linear's own GitHub integration moves issues to `Done` on PR-merge, so the platform *already* writes the terminal rung natively; fighting that with labels means two ledgers.
- **The claim rungs and the triage vocabulary compete for one single-select dimension — the claims win it.** ADR-0015 forecast "Linear = workflow-state" for the *triage* dimension, before the claim mapping was decided. Ground truth (the server pilot's `des`/`dev` teams): the standard workflow has no `needs-info`/`ready-for-human` columns, the `started`-type states are needed by the claim ledger, the contract requires the eligibility state's native string to equal the OR-set token, and the consumer's real issues already carry `ready-for-agent` **as a label**. The forecast is corrected by amendment on ADR-0015; the triage vocabulary keeps GitHub parity (labels), with two targeted native touches where Linear is genuinely state-shaped: `closeUnplanned` → the **`Canceled`** state (the Linear `Canceled`-category state flotilla's `unplanned` rung maps to — the rung GitHub closes with its own `not_planned` reason; that token is GitHub's, not Linear's), and `applyTriage` clears Linear's Triage inbox (`Triage → Backlog`) as ADR-0004-class best-effort cosmetics.
- **The human-drag hazard is accepted, not engineered away.** `Todo` is a human-used column; a hand-dragged issue reads as `queued` and conservatively shrinks the next wave's candidate pool. Per ADR-0002 the ledger is a lossy projection and the spine is the WAL authority — drift reconciles at `wave-resume`. Consumer convention (the server pilot: humans park in `Backlog`, `Todo` means wave-claimed) + the config-mapped state names keep this honest and portable.

## Considered Options

- **Claims as workflow states, vocabulary as labels, config-mapped state names** (chosen) — board = live wave dashboard; rides the platform's own PR-merge → `Done` motion; portable via `states` config.
- **Claims as `wave/<rung>` labels (full GitHub parity)** (rejected) — collision-free but blind on the board; label-spam is un-idiomatic on Linear; fights the GitHub integration's native state moves.
- **Hybrid: `queued` as label, `in-flight`/`in-review` as states** (rejected) — two mechanisms for one dimension, and the queued rung (the soft claim humans most need to see at planning time) is exactly the one hidden from the board.
- **Triage vocabulary as workflow states (ADR-0015's original forecast)** (rejected) — needs 3+ custom states per consumer team, collides with the claim mapping for the `started` types, and breaks the eligibility-token = label identity the consumer already lives.
- **Native blocked-by relations for `blockedBy`, both directions, now** (deferred, read-side taken) — **read = union** of body-codec ∪ native relations from day 1 (without it the DoR gate is blind to the consumer's existing native relations — a dispatch-too-early correctness hole), **write = body-codec** in this slice; native write is the declared fast-follow (id-resolution + idempotent updates, pure refinement once the adapter stands).
- **Closing probe cross-checking the GitHub API** (rejected) — one seam, one auth; Linear's GitHub-integration attachments already carry the PR merge status. `getClosingState` reads: state-type `completed` + merged-PR attachment → `merged`; a **non-merged** attachment present → `closed-unmerged` (a proven rejection → needs-attention, ADR-0005); a `completed`/`canceled` state with **no attachment at all** → `closed-unknown` (see the fourth-outcome note in Consequences); else `open`. Operational preconditions (checked by `wave-setup`): the GitHub integration is installed and wave PRs carry the magic word (`Fixes DES-NN`) — the tracker-dependent close phrase comes from config.
- **UUID as the opaque id** (rejected) — magic words, branch names, spine rows, and humans all speak `DES-16`; ADR-0001 wants the tracker-native *human-visible* identifier. The UUID is a seam-internal lookup detail.

## Consequences

- **`LinearStoreConfig`** joins the `StoreConfig` union: `{ kind: 'linear', team, project?, eligibility?, states?, categoryLabels? }`. `team` is required (owns workflow + label namespace); `project` is the candidate-pool filter (`listOpen` draws only project issues when set — the server pilot binds `des` + `Mock Server`); `states` maps rungs to column names (defaults above); `categoryLabels` maps schema categories to existing consumer labels (the server pilot: `bug`→`Bug`, `enhancement`→`Improvement`).

  **Amendment 2026-09-16 — `states` is six keys, not four: `unclaimTarget` and `unplanned` are typed and documented.** The line above is accurate about what `states` MAPS and was incomplete about what it CARRIES. The adapter's `LinearStateMap` has always had five required members — the three rungs plus `unclaimTarget` (default `Backlog`, where `unclaim()` parks a released claim and where `applyTriage()` clears Linear's `Triage` inbox to) and `unplanned` (default `Canceled`, where `closeUnplanned()` lands — the Linear `Canceled`-category state flotilla's `unplanned` rung maps to, and GitHub's `not_planned` reason with it; that token is GitHub's `state_reason`, not Linear vocabulary) — and the config block declared only the rungs plus the later `doneState`. Both untyped keys were nonetheless HONOURED at runtime: the store factory hands `store.states` through un-picked and the adapter merges it over `DEFAULT_LINEAR_STATES`, so an undeclared key reached the store by accident of that merge, and one shipped consumer has been relying on `unclaimTarget: "Todo"`. `LinearStateMapConfig` now declares both, `wave-config.spec.ts` pins its key set as EQUAL to the adapter's by a type-level assertion (with negative controls in both directions) so the two cannot drift apart again, and `wave-setup`'s tables document all six with their defaults. No behaviour changed and nothing was renamed, removed or re-typed — this is additive (Minor, ADR-0035): what changed is that a typo in either key is now a COMPILE error for a TypeScript author annotating the block against `LinearStateMapConfig`, and that the documented shape matches the shape the adapter reads. That check lives only in the type — `config validate` still tolerates an unknown key under `states`, deliberately: this row added no loader validator for the block, and a config carrying `unclaimTargets` passes validation exactly as it did before. The refusal ladder for a state NAME is unmoved and stays where this ADR put it: the live team catalog, probed by `store-preflight`'s `state-catalog` check, which verifies the configured value rather than the default.
- **`LinearApi` seam** mirrors the `GitHubApi` shape (create/get/list, label add/remove, comment, state set, relations read, closing probe) with an in-memory fake; the conformance suite runs unchanged against `LinearIssuesStore` — the same zero-change bar `GitHubIssuesStore` passed in P3.
- **body-codec relocates** from `adapters/github/` to a shared adapter home; the GitHub store's imports update, behavior byte-identical.
- **ADR-0015 is amended** (identity row: Linear = labels for the vocabulary; state only for `unplanned` + inbox cosmetics). CONTEXT's Triage-facet and Claim entries update accordingly.
- **The M1 §6 live gate re-scopes to this adapter's consumer**: one real wave on the server pilot's **Mock Server** project — it exercises the Linear tracker adapter *and* the full GitHub git-host side (worktrees, PRs against protected `main`, magic-word close). The wiki pilot's GitHub-Issues live run moves to M2-optional; `RealGitHubApi` stays fixture-proven until a GitHub-Issues consumer materializes.
- **Fast-follows on record:** native blocked-by *write* (the consumer wants it — their existing issues use native relations); `listTriage` batch analytics stays M2 (ADR-0015).

### Amendment — the closing probe's fourth outcome (`closed-unknown`; W2-F1c, FOR-23/FOR-20)

The closing probe was first specified with three outcomes (`open | merged | closed-unmerged`). A live wave (`2026-07-16-hardening-w2`) exposed the gap: an issue from a prior wave resolved to `done` **outside flotilla** — the most plausible cause a tracker-integration side effect of its id being named in another PR's title/body (the Convention-4 mention-footgun). The probe read that close as `closed-unmerged`, and the done-reconcile flags `closed-unmerged` as `recoverable-stop` — so a legitimately-finished row was reported as a rejected PR. The probe had conflated two different situations: **(a)** a closing PR exists and was closed without merging (a real rejection worth a human stop), and **(b)** the issue is closed but the probe found *no closing-PR evidence at all*.

`ClosingState` is therefore widened to a **fourth outcome**, `closed-unknown`, and every outcome is read as **an evidence claim, not a verdict** — the probe reports what it *found*, never what it inferred from an absence:

- `merged` — positive evidence a linked PR merged (the wave's done signal).
- `closed-unmerged` — positive evidence a linked PR was **found** and did **not** merge: a genuine rejection → `recoverable-stop`.
- `closed-unknown` — the issue is closed but **no PR evidence was found either way** (a hand-close, a duplicate, a foreign-id mention, or a workspace whose integration never attached a PR). *Absence of evidence, not evidence of rejection.* Callers **MUST NOT** treat it as a rejection: it is **reported** (and, via the ADR-0023 evidence hierarchy, falls to `host-pr status` for a merge the tracker missed), **never auto-flagged**.

Per-adapter honesty is the rule the shared conformance suite now enforces (FOR-20, no longer 0-diff on this behavior): **Linear** and **GitHub** can record a rejected PR (a non-merged attachment / a `closedByPullRequestsReferences` node) and so emit `closed-unmerged` for it; **MarkdownFs** structurally cannot prove a rejection — it has only "a PR merged" (the `**Closed-by:**` ref) or "no ref" — so it emits `closed-unknown` and **never** `closed-unmerged`, refusing to claim a rejection it cannot see. `wave-close` and `wave-resume` both read the outcome the same way: `closed-unmerged` → flag `recoverable-stop`; `closed-unknown` → report, consult the host, never auto-flag.

### Amendment 2026-09-17 — `not_planned` is GitHub vocabulary; the unplanned rung is a three-way mapping

Three sentences of this ADR — and the `wave-setup` tables and `wave-config`/adapter doc comments they seeded — called the `Canceled` state "Linear's `not_planned`". **The default VALUE was and is correct (`Canceled` is Linear's own stock name); the ATTRIBUTION of the token was not**, and no verify profile gates a vendor-factual claim made in prose, so it survived two rows.

Checked against the vendors themselves rather than from memory:

- **Linear** — its workflow documentation (<https://linear.app/docs/configuring-workflows>) enumerates six status **categories** — `Backlog`, `Unstarted`, `Started`, `Completed`, `Canceled`, `Duplicate` — and names `Triage` apart from that list, as "an additional status category that acts as an Inbox for your team"; it gives the shipped default workflow as `Backlog > Todo > In Progress > Done > Canceled`, and carries **no `not_planned` vocabulary anywhere**.
- **GitHub** — `not_planned` is a value of the issue `state_reason` body parameter on the REST "Update an issue" endpoint, documented as `completed | not_planned | duplicate | reopened | null`; this repo's own `GhStateReason` types the subset it consumes, `completed | not_planned | reopened | null`.

So read the unplanned rung as one CROSS-TRACKER mapping: **flotilla's `unplanned` rung ↔ Linear's `Canceled` status category ↔ GitHub's `not_planned` state reason**. Every prose site that names the default now says that instead of naming a GitHub token as a Linear column. Wording only — no config value, no default and no adapter behaviour changed by this amendment.

### Note 2026-09-17 (second of the day) — two sentences above have been overtaken: `config validate` now warns on an unknown `states` key, and `GhStateReason` carries `duplicate`

Both sentences below were accurate when written. Neither is rewritten — an amendment's text is the record of what was decided on its date, and correcting it in place would erase the fact that the world moved afterwards. This note is the correction; read it as the current reading of both.

- **The 2026-09-16 amendment says "`config validate` still tolerates an unknown key under `states`, deliberately".** That was true of the tip it was written against. Issue #761's config warnings have landed since: `config validate` now REPORTS an unknown key under `store.states`, naming the six keys the block declares (`queued`, `inFlight`, `inReview`, `unclaimTarget`, `unplanned`, `doneState`), so a config carrying `unclaimTargets` comes back one line away from the spelling that works. What survives of the original sentence is its stance, which was never about silence: it is a **warning and not a refusal**, and it **moves no exit code** — a config that validates today keeps validating and still exits 0, because `wave.config.json` is a semver contract (ADR-0035) and a new refusal on it would be a major. The refusal ladder for a state NAME is still the live team catalog probed by `store-preflight`'s `state-catalog` check, exactly as the amendment left it.
- **The 2026-09-17 amendment above says this repo's `GhStateReason` "types the subset it consumes, `completed | not_planned | reopened | null`".** That subset has since been widened by one member: `duplicate`, the fourth of the five values GitHub's REST *Update an issue* endpoint documents. The widening is **read-side only** — the adapter's projection of a fetched issue now carries a `duplicate` close as `duplicate` instead of flattening it to `null`, so the seam stops discarding a distinction GitHub makes. Nothing about the WRITE path changed: `nativeClose` still sends `completed` or `not_planned` and nothing else, and flotilla still has no verb that closes an issue as a duplicate. Nor does the closing probe move: a `duplicate` close carries no closing-PR evidence of its own, so `read-closing` derives exactly what it derives for a `not_planned` close — the same closing class, on the same evidence rule (`closed-unknown` where no closing PR was found; absence of evidence, never a rejection, per the `closed-unknown` amendment above). With `duplicate` in, the type now spells all five documented values and no longer types a proper subset of them.

### Amendment 2026-09-21 — Linear's own PR-automation is a documented operational precondition, not a probed fact (issue #756)

**The gap.** On a Linear store whose team leaves the GitHub integration's PR automation on Linear's own shipped default, opening a Worker's pull request moves the linked issue to the plain `In Progress` state — Linear's own default target for that trigger, not necessarily this config's `states.inFlight`. This store's `rungOf` only recognizes a state NAME that equals a configured rung, so the read-back diverges by exactly which name collides: a target this config's map does not recognize at all reads the row `available` — unclaimed, and re-eligible for a concurrent wave to claim out from under the Worker genuinely on it; Linear's stock `In Progress` name, when it happens to differ from this consumer's own `states.inFlight`, instead reads `in-flight` — a silent downgrade from whatever rung the row was actually on (typically `in-review`, once the PR is open for review). Which of the two a given consumer hits depends on its own unrecorded `states` block; both are documented here, neither is asserted as the one observed. The merged-direction move (`Done` on PR-merge) was already documented above as the wanted signal `close()` relies on; the opened-direction move was documented nowhere, and `wave-setup` overstated what its own `tracker-host-integration` probe reads — the preconditions list, the Linear-key section, and setup-mechanics.md's check table all read as though a `pass` confirmed a team-or-repository binding. It does not: `hasGitHubIntegration()` (`real-linear-api.ts`) reads WORKSPACE-level integration presence only, carrying no team or repo filter, and all three sites now say so.

**Automation is a precondition, not a probe.** `wave-setup`'s Linear operational preconditions gained a sixth human-confirmed item: the team's PR-automation, configured at Linear's own per-team settings path — **Settings → Team → Workflows & automations → Pull request and commit automations** (read from Linear's own documentation on this date) — must be aligned to this config's claim states, never left on the shipped default.

**The alignment rule** maps Linear's automation triggers onto this store's rungs directly: PR opened/drafted → the state `states.inFlight` names; review requested or the PR reaches mergeable status ("ready for merge") → the state `states.inReview` names; merged → Linear's own Done-on-merge automation stays on, unchanged (the direction already documented above).

**Exact-name derivation.** Alignment means Linear's automation setting at each trigger names the SAME workflow-state string this config's `states` block names for that rung, not merely a same-category state — the identical case-sensitive exact-name discipline this ADR already holds the team key and the `state-catalog` probe to. A team overriding `states.inFlight` away from `In Progress` (or `states.inReview` away from `In Review`) must set that automation trigger to the SAME overridden name.

**Deliberately not probed.** `store-preflight`'s `tracker-host-integration` check stays scoped to workspace-level integration presence; it does not read a team's automation mapping. Whether Linear's API exposes that mapping as a readable field at all is an open schema question, tracked separately (issue #879) rather than answered here.
