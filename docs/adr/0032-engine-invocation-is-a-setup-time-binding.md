# Engine invocation is a single setup-time binding (`engine.cli`), never a runtime fallback

ADR-0031's class-(c) rule had every `{{wave-cli}}` resolution block state a **dual form** — published-package form first (`npx @formtrieb/flotilla-engine`), vendored form as documented fallback — and left the choice to the executing agent at invocation time. Live evidence killed that shape three ways. (1) **Silent divergence:** on 5 of 7 rows of wave `2026-07-29-publish-prep-and-guards` the npm-first form failed (missing resolver / `ECOMPROMISED` shared-cache locks under fan-out / npx-shim exit-127) and every Worker fell back to the vendored form without anyone deciding that — the documented default was operationally dead for weeks before #231 surfaced it. (2) **Doc drift:** by 2026-07-30 the two authorities disagreed about which form even *is* the default (`workflow-driver.md` said npm package; `setup-mechanics.md` said npx-free local binary) — the predictable failure mode of a decision living as prose in several places. (3) **Measured cost:** disclosure 250.7 of wave `2026-07-30-arm-and-wiring` timed the npx form at **~82 s per invocation** against ~1.2 s for a local binary — npm registry resolution runs on every npx call even with a warm cache; a wave-create's ~22 engine calls turn into 30 minutes versus 30 seconds, and the cost falls hardest on exactly the consumer npm-first was designed for: one with no vendored checkout to fall back to. Settled in a grill session 2026-07-30.

## Decision

- **`engine.cli` is a field in `wave.config.json`: a single authoritative command string, resolved host-side at brief-compose time.** Skills stop stating invocation forms; they read the configured value. `config validate` gates the field; `wave-setup` authors it. Fail-loud, per the ADR-0029 principle (*configured means authoritative*): if the configured form fails, that is a STOP/needs-attention finding — a broken install, config, or release — never a cue to try another form. Invocation fallback chains are abolished.
- **Every consumer binds to a pinned local install: `./node_modules/.bin/flotilla-engine`.** `wave-setup` scaffolds `@formtrieb/flotilla-engine` as a devDependency — including for non-Node consumers, where it scaffolds a minimal tracked `package.json` + lockfile and prepends `npm ci` to `depsSetup` (the engine needs a Node runtime regardless; the one-line manifest merely makes the existing prerequisite explicit and worktree-resolvable). `npx` is demoted to one-time bootstrap ("try flotilla before wave-setup has run") and disappears from every wave-operational path. The allowlist scaffold's engine entries shrink from four-to-six speculative forms to the one configured form (plus its env-prefixed twin).
- **flotilla itself binds to the vendored form** (`./tools/wave/node_modules/.bin/tsx tools/wave/src/cli.ts`) — it builds what it runs. This dissolves the "waves touching the engine CLI must run vendored" exception: for this repo the configured value *is* the vendored form.
- **Lockstep is a checked invariant, not a habit.** `plugin.json` and the npm package already carry the same version per release; that equality becomes enforced wherever `engine.cli` points at the installed binary: `wave-start`'s gate phase compares `engine.cli --version` against the plugin version at the skill's own resolution anchor and **STOPs** on mismatch (repair in the message: `npm i -D @formtrieb/flotilla-engine@<plugin-version>`); `store-preflight` reports the same check advisory at setup/plan time. Exact equality pre-1.0; loosening is a post-1.0 decision. In the source-form repo the check is vacuous — skills and engine come from the same SHA by construction.
- **The pattern behind both layers gets a name: source form / installed form** (CONTEXT.md `### Distribution`). Skills and engine each exist in a source form (local `.claude/skills/`, vendored `tools/wave`) and an installed form (plugin, npm package). A repo runs exactly one form per layer, statically bound through tracked config — `enabledPlugins` self-disable for the skills layer, `engine.cli` for the engine layer. Mixed forms are the defect both bindings exist to prevent. **Dual-form** narrows to prose references only.

## Considered Options

- **Fallback chain in `engine.cli` (array, try in order)** — rejected: silent fallback is precisely what masked the #231 signal; robustness against a broken form belongs to needs-attention visibility, not to quiet rerouting.
- **Binding as an env var in the tracked settings env block** — rejected: a command held in a shell-expanded variable is the Convention-12 exit-127 class (five live occurrences), and the settings file is harness config, not wave domain.
- **Plugin-clone as CLI provider** (invoke the engine from `~/.claude/plugins/…`) — rejected on structure, not taste: the clone ships no `node_modules` (the engine has runtime deps), and the path is absolute and machine-specific — the tracked allowlist a Worker worktree inherits can only carry repo-relative prefixes, so every AFK Worker would stall at the permission gate.
- **npx for non-Node consumers only** — rejected: it preserves a second operational form for a whole consumer class, with the measured 82 s/call latency and the documented cache-contention workaround as permanent baggage; a one-line `package.json` in a PHP repo is the smaller imposition, and uniformity (one consumer form everywhere) is itself consumer-friendliness.

## Consequences

- ADR-0031's class-(c) dual-form **invocation** rule is superseded (amendment note there); classes (a)/(b) and the reference guard are untouched. CONTEXT.md: **Dual-form** re-scoped to prose references, **Source form / Installed form** added.
- Implementation slices: the `engine.cli` config field + `config validate`; the version-equality gate (`wave-start` STOP, `store-preflight` advisory); `wave-setup` scaffold changes (devDependency, non-Node `package.json`, shrunken allowlist block); resolution-block rewrites in the skills; the workflow-driver's `WAVE_CLI` constant filled from config.
- The default-form doc drift becomes structurally impossible: the default lives in one place (`wave-setup`'s scaffold value), everything else reads config.
- Related editorial decision from the same grill, deliberately **not** ADR-material (reversible, no hard trade-off): citation-placement convention for skill prose (rule + one-line why in place, deep provenance in reference files / provenance positions), to land as a wave-shared convention with a reference-guard predicate and a shrinking legacy allowlist.
