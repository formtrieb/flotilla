# The mirror pass publishes derived accounting to the container's native update surface

ADR-0045 decision 6 deferred the "health write-mirror" — publishing the goal station's frontier report as a native Linear Project Update — as a named follow-up (#596), with demand observed at the live consumer (an Operator who reads health independently of flotilla, and hand-built update-writer skills already in production there). The hazard was equally observed: ADR-0044's requirements arrived as counter-examples, one of them an agent that wrote itself a release authorization into a planning tool's free-prose notes — and a Linear Project/Initiative Update is exactly such a durable free-prose surface, with **Health** (an authored judgment: `onTrack / atRisk / offTrack`) coupled to it. A 2026-08-16 grill settled the design against the consumer's lived template (the `project-update` skill in the projektionisten-skills repo: narrative documentation with thematic sections and a "next up" close, a health *proposal with one-sentence reasoning* that the human confirms, and an explicit release before any publish) — which falsified the numbers-only render the first design draft assumed, and reshaped the answer to the free-prose hazard.

## Decision

1. **A fourth pass, `mirror`, on the goal station — the status pass stays read-only, literally.** The mirror is a writing pass like cut and curation: it previews its one write in full and takes an explicit per-pass confirm; no pass inherits an earlier pass's approval. The name is deliberate: the pass mirrors the **Frontier**, not health — the ticket's working name "health write-mirror" is retired (what is mirrored is derived accounting; health only ever travels as a transcribed or source-attributed human judgment, decision 4).
2. **One facet verb — `publishGoalUpdate(goalId, { narrative?, health?, operatorNote? })` — and the engine derives the frontier fresh at write time.** The caller never supplies the report: the mirror structurally cannot lie about the frontier because it is never told it (the same class of guarantee as the triage facet's inability to reach the claim ledger). The pass's preview carries the freshness caveat — the published derivation may differ from a status report shown minutes earlier if the tracker moved.
3. **The update body is two layers: a consumer-styled narrative above an engine-owned anchor.** The narrative — what happened and why it matters, documentation rather than a ping — is session-drafted in the consumer's own form and language (the consumer's house template is the style source; flotilla pins no form), and **every sentence passes the Operator's explicit confirm**: the confirm is what makes it Operator prose, the lived template's own release step. The **anchor** is the engine's deterministic render of the fresh frontier — per member: name (as a native link), native state, the member's **own** health, unresolved blockers — plus the distribution in plain reader-facing language and a provenance line naming the mirror pass; it can be neither supplied nor edited nor omitted by the caller. A narrative that embellishes stands directly beside an anchor that counts — the contradiction is visible inside the artifact itself, which is the realistic form of the audit property once prose is admitted. On an empty frontier the anchor carries the accounting sentence verbatim: every member is closed, and the remaining step — closing the container — is the Operator's act in the tracker.
4. **Health is never derived from the frontier — two sanctioned sources only.** (a) The Operator supplies or confirms a value: the station transcribes a human judgment, the same figure as closing the container being the Operator's act. (b) The station may **propose** an aggregation of the members' own healths — themselves human-authored native judgments, written by the consumer's own per-project flow — **source-attributed** ("atRisk — inherited from *<member>*"), confirmation required, never a silent default. A formula over the station's own classification ("blocked > 0 → atRisk") is the station judging, and stays forbidden. With no member healths and no Operator value, the update publishes without health; if the native create surface *forces* a value in that case, the pass refuses typed rather than defaulting — whether it forces one is a build-time schema verification item, not an assumption.
5. **The surface follows the container binding, one update per goal.** Project-bound → a native Project Update; initiative-bound → a native Initiative Update. **No per-member fan-out:** fine-grained per-project updates remain the consumer's own flow (the lived template's territory) — the goal update complements them, names every member with state, health and link in its anchor (so "which member is red" is answered inside the goal update, which a single container-level health enum cannot do), and the two layers cite rather than duplicate each other. A store whose bound container has no native update surface (GitHub Milestone, MarkdownFs goal file) refuses typed — the unrealized-container pattern, one surface over; a milestone-description edit as a substitute was rejected as a lossy state write.

## Considered Options

- **The status pass gains a publish arm** (rejected) — "the status pass is read-only and needs no confirm" would hold only with a footnote, and footnoted safety guarantees are the expensive kind.
- **Numbers-only deterministic render, no narrative** (rejected) — falsified by the consumer's lived template: the artifact's observed value *is* the documentation of what happened. The answer to the free-prose hazard is confirm-per-sentence plus the unfalsifiable anchor, not prose prohibition.
- **Frontier-derived health** (rejected) — the station judging by formula; ADR-0044's owes-accounting-never-the-declaration line, which decision 4's member-health aggregation deliberately does not cross (it aggregates *human* judgments, attributed).
- **The verb accepts a caller-supplied report** (rejected) — a doctored-report channel; engine-derives-fresh is the structural guarantee that the mirror cannot lie about the frontier.
- **Per-member updates beside the goal update** (rejected) — N+1 confirm surfaces per pass, and station-authored member updates would be contentless duplicates of the consumer's real per-project narratives, polluting member timelines.
- **A consumer-side raw-API skill instead of a facet verb** (rejected) — the raw-call class the credential seam already retired once; and only an engine verb can pin the anchor's honesty.

## Consequences

- **#596 sharpens to the engine slice**: the facet verb, both Linear realizations (`projectUpdateCreate` / `initiativeUpdateCreate`), typed refusals on github/markdown, conformance across all three stores. `LinearApi` widens by required method(s) — the public-surface heads-up rides the release-notes bundle at build time, per the established pattern. Build-time verification items pinned there: `initiativeUpdateCreate` existence, health-field optionality on both create surfaces (decides decision 4's refusal arm), and a read-back of one UI-created update.
- **The anchor needs per-member native state and member health from the frontier derivation** — #609 (the frontier-native-member-state follow-up, filed this session from the initiative-skill row's disclosed engine gap) is the natural carrier; the two slices should be planned together.
- **The skill slice files separately** (the mirror pass on the goal station), blocked by the engine slice — the ADR-0045 engine/skill split, repeated.
- **CONTEXT.md gains the Mirror pass entry** (this PR).
- **Consumer note (DSW21):** initiative updates will exist in that workspace for the first time; the read-skills there (activity-summary, stakeholder-pdf) may want to recognize the anchor's provenance line. The consumer's "nobody hand-writes initiative updates" convention stays literally true — the mirror is precisely not hand-written.
