# A goal's members are the container's direct native members

ADR-0044 shipped the Goal facet with the Linear **Project** realization only and deferred **Initiative** as a named follow-up (#573): initiatives hold projects, not issues, so membership is transitive and "may not even be `assignToGoal`-shaped — a contract-shape question worth its own design." A grill on 2026-08-15 settled that design against the live consumer's actual workspace rather than against assumptions: the DSW21 Linear workspace (the recorded Initiative=Epic / Project=User Story consumer) holds nine initiatives whose nineteen member projects carry **thirteen empty ones** — the consumer's planning lives in the *existence of projects*, exactly the "existence first" unit ADR-0044 decision 1 named at issue granularity. That structure falsified the transitive read the deferral had half-assumed: an issue-flattening frontier on the "Unternehmen verwalten" initiative (seven stories, six empty, one backlog issue) would report **complete** after one issue closes, six unbuilt stories notwithstanding; an initiative with zero projects ("Firmenadmin", Proposed, never started) would read complete out of the gate. `actionable` is a positive claim, and a frontier structurally blind to empty members cannot make it honestly.

## Decision

1. **A Goal's members are the bound container's direct native members — the member kind follows the binding, never a flattening query.** Issues for the issue-direct containers (GitHub Milestone · Linear Project · MarkdownFs goal file — byte-identical to what shipped), projects for a Linear Initiative. ADR-0044 decision 2's "issue-set boundary" sentence refines rather than falls: a Goal bounds *natively-queryable work units*; completion stays a query because a Linear project has native closed state exactly as an issue does. The goal's issue-set remains derivable through member projects, but it is never the member set. CONTEXT.md's Goal and Frontier entries carry the amendment in this PR.
2. **One frontier vocabulary at every member granularity.** `GoalFrontier`, the five readings, and `computeGoalFrontier` are untouched — the adapter states {@link GoalMemberFacts} honestly per member kind: `closed` ← project `completed`|`canceled` (the issue rule's mirror); `claimed` ← `started`|`paused`, or ≥1 wave-claimed open issue inside; `eligible` ← ≥1 open issue inside carrying the eligibility marker; `unresolvedBlockers` ← native project relations whose other side is not closed. Consequences at the live structure: an empty project reads `unready` for exactly the reason a bare ticket does; an all-untriaged story reads `unready` (sharpen first, then drawable); a story handed to another team and worked outside flotilla never counterfeits `actionable` — that reading stays the literal claim "a wave could draw here now." `paused` reads `in-motion` because `blocked` asserts a *named* unresolved dependency, which paused lacks; the station's report shows the native state alongside the classification. Linear's own health surfaces (Project Updates) remain the tracker's sight layer — the frontier complements them with wave-drawability truth, never replaces them.
3. **The write verbs generalize member-kind-generically.** `assignToGoal(goalId, memberId)` joins a direct member by curation — the id kind follows the binding and is **validated against it**: an issue-shaped id at an initiative-bound call refuses typed before any write, because that call site is precisely where the transitive confusion ("I meant the issue *inside* the goal") would otherwise pass silently — the goal-id/issue-id id-space hazard, one seam over. `createGoal` mints an initiative natively. A new facet verb **`createGoalMember(goalId, input, container?)`** mints a **bare direct member and joins it in one act**: under the issue-direct bindings the shipped bare-issue create plus the join (the station gets one path instead of two); under `initiative` a project minted under the api's configured team plus the native initiative join. A Linear project is *born* bare — name, prose, `backlog`, no eligibility semantics — so the bare-invariant burden that would have argued against this verb does not exist at project granularity. Team handover after a cut (the consumer's Design→Dev flow) is a tracker-UI act the frontier tolerates by construction: goal reads are team-agnostic. Creation stays goal-anchored; free-floating project creation remains tracker admin, not facet surface. No-partial-application by pre-validation (goal id and binding resolve before any mint); if the join still fails after the mint, the typed error names the minted member id loudly — residue is reported, never silently rolled back (the `closed-unknown` honesty line).
4. **The `blockedBy` arm rides on `createGoalMember`, realized natively per member kind — the dependencies are the feature.** The timeline motivation that filed #573 is dependency *sight at goal granularity*; the station writes the edges it knows at the cut instead of the Operator hand-clicking them post-hoc (the misplaced-block error class the grill named). Under `initiative` the edge is a native project relation (`projectRelationCreate`; read back via `Project.relations`/`inverseRelations` — write surface verified against Linear's published schema 2026-08-15; the relation `type` string is typed free-form there, so its value is pinned at build time by one UI-created edge read back). Under the issue-direct bindings it is ADR-0044's shipped arm unchanged. A store that cannot represent the edge refuses typed before any write — the `bare-blocked-by-unrepresentable` precedent, one member kind over.
5. **`listGoals` under `initiative` lists workspace-wide** — a deliberate, documented divergence from the project realization's team scoping. Initiatives live above teams (the consumer's span Design and Dev), so a team filter would silently hide cross-team finish lines; the width costs nothing because `listGoals` is sight, never the wave candidate set.
6. **Two named deferrals, not silent caps**, each filed bare with this ADR as provenance: the wave-plan goal panel's transitive issue∈goal closure under initiative binding (the goal station's status pass is the sight surface; whether the panel is missed is a practice question), and the v2 **health write-mirror** (publishing the frontier report as a native Project Update through the facet — demand observed at the consumer, which already runs hand-built update-writer skills).

## Considered Options

- **Issue-shaped transitive membership** (rejected) — the falsifying evidence above; the frontier would lie precisely where the consumer keeps its planning.
- **A second, project-shaped frontier vocabulary** (rejected) — the classification rule is the engine's one seam; the adapter maps facts, the engine never grows lookalike ladders.
- **Sight-only realization (reads transitive, writes refuse)** (rejected) — the write half is where the misplaced-block error class dies, and every write has a real native target; asymmetry bought nothing.
- **`assignProjectToGoal` as a separate verb** (rejected) — a second surface for the same semantic; the member kind is the binding's fact, not the verb's.
- **Cut pass files no members under initiative** (rejected by the consumer's own cost model) — everything but the initiative hand-made, recurring at every grill's follow-up filing; and the bare-invariant burden the option assumed does not exist for projects.
- **Team-scoped `listGoals` under initiative** (rejected) — hides cross-team finish lines silently; the honest scope is the container's own.

## Consequences

- CONTEXT.md **Goal** and **Frontier** amended: members are the container's direct native members; one vocabulary at every member granularity (this PR).
- #573 sharpens to the engine realization (contract generalization `issueId`→`memberId`, `createGoalMember` with the `blockedBy` arm, the Linear initiative realization, fake substrate, conformance — barrel and guard extensions ride the same diff). The goal-*skill*'s passes under initiative binding and the health write-mirror file as separate bare issues; `initiative` leaves `GoalBindingError: 'unrealized-container'` on Linear only when that engine issue lands.
- This ADR lands Coordinator-direct (ADR-0033: it closes no issue).
