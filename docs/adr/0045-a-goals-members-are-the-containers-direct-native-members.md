# A goal's members are the container's direct native members

ADR-0044 shipped the Goal facet with the Linear **Project** realization only and deferred **Initiative** as a named follow-up (#573): initiatives hold projects, not issues, so membership is transitive and "may not even be `assignToGoal`-shaped — a contract-shape question worth its own design." A grill on 2026-08-15 settled that design against the live consumer's actual workspace rather than against assumptions: the server pilot's Linear workspace (the recorded Initiative=Epic / Project=User Story consumer) holds nine initiatives whose nineteen member projects carry **thirteen empty ones** — the consumer's planning lives in the *existence of projects*, exactly the "existence first" unit ADR-0044 decision 1 named at issue granularity. That structure falsified the transitive read the deferral had half-assumed: an issue-flattening frontier on the "Unternehmen verwalten" initiative (seven stories, six empty, one backlog issue) would report **complete** after one issue closes, six unbuilt stories notwithstanding; an initiative with zero projects ("Firmenadmin", Proposed, never started) would read complete out of the gate. `actionable` is a positive claim, and a frontier structurally blind to empty members cannot make it honestly.

## Decision

1. **A Goal's members are the bound container's direct native members — the member kind follows the binding, never a flattening query.** Issues for the issue-direct containers (GitHub Milestone · Linear Project · MarkdownFs goal file — byte-identical to what shipped), projects for a Linear Initiative. ADR-0044 decision 2's "issue-set boundary" sentence refines rather than falls: a Goal bounds *natively-queryable work units*; completion stays a query because a Linear project has native closed state exactly as an issue does. The goal's issue-set remains derivable through member projects, but it is never the member set. CONTEXT.md's Goal and Frontier entries carry the amendment in this PR.
2. **One frontier vocabulary at every member granularity.** `GoalFrontier`, the five readings, and `computeGoalFrontier` are untouched — the adapter states {@link GoalMemberFacts} honestly per member kind: `closed` ← project `completed`|`canceled` (the issue rule's mirror); `claimed` ← `started`|`paused`, or ≥1 wave-claimed open issue inside; `eligible` ← ≥1 open issue inside carrying the eligibility marker; `unresolvedBlockers` ← native project relations whose other side is not closed. Consequences at the live structure: an empty project reads `unready` for exactly the reason a bare ticket does; an all-untriaged story reads `unready` (sharpen first, then drawable); a story handed to another team and worked outside flotilla never counterfeits `actionable` — that reading stays the literal claim "a wave could draw here now." `paused` reads `in-motion` because `blocked` asserts a *named* unresolved dependency, which paused lacks; the station's report shows the native state alongside the classification. Linear's own health surfaces (Project Updates) remain the tracker's sight layer — the frontier complements them with wave-drawability truth, never replaces them.
3. **The write verbs generalize member-kind-generically.** `assignToGoal(goalId, memberId)` joins a direct member by curation — the id kind follows the binding and is **validated against it**: an issue-shaped id at an initiative-bound call refuses typed before any write, because that call site is precisely where the transitive confusion ("I meant the issue *inside* the goal") would otherwise pass silently — the goal-id/issue-id id-space hazard, one seam over. `createGoal` mints an initiative natively. A new facet verb **`createGoalMember(goalId, input, container?)`** mints a **bare direct member and joins it in one act**: under the issue-direct bindings the shipped bare-issue create plus the join (the station gets one path instead of two); under `initiative` a project minted under the api's configured team plus the native initiative join. A Linear project is *born* bare — name, prose, `backlog`, no eligibility semantics — so the bare-invariant burden that would have argued against this verb does not exist at project granularity. Team handover after a cut (the consumer's Design→Dev flow) is a tracker-UI act the frontier tolerates by construction: goal reads are team-agnostic. Creation stays goal-anchored; free-floating project creation remains tracker admin, not facet surface. No-partial-application by pre-validation (goal id and binding resolve before any mint); if the join still fails after the mint, the typed error names the minted member id loudly — residue is reported, never silently rolled back (the `closed-unknown` honesty line).
4. **The `blockedBy` arm rides on `createGoalMember`, realized natively per member kind — the dependencies are the feature.** The timeline motivation that filed #573 is dependency *sight at goal granularity*; the station writes the edges it knows at the cut instead of the Operator hand-clicking them post-hoc (the misplaced-block error class the grill named). Under `initiative` the edge is a native project relation (`projectRelationCreate`; read back via `Project.relations`/`inverseRelations` — write surface verified against Linear's published schema 2026-08-15; the relation `type` string is typed free-form there, so its value is pinned at build time by one UI-created edge read back). Under the issue-direct bindings it is ADR-0044's shipped arm unchanged. A store that cannot represent the edge refuses typed before any write — the `bare-blocked-by-unrepresentable` precedent, one member kind over.
5. **`listGoals` under `initiative` lists workspace-wide** — a deliberate, documented divergence from the project realization's team scoping. Initiatives live above teams (the consumer's span Design and Dev), so a team filter would silently hide cross-team finish lines; the width costs nothing because `listGoals` is sight, never the wave candidate set.
6. **Two named deferrals, not silent caps**, each filed bare with this ADR as provenance: the wave-plan goal panel's transitive issue∈goal closure under initiative binding (the goal station's status pass is the sight surface; whether the panel is missed is a practice question), and the v2 **health write-mirror** (publishing the frontier report as a native Project Update through the facet — demand observed at the consumer, which already runs hand-built update-writer skills).

## Considered Options

- **Issue-shaped transitive membership** (rejected) — the falsifying evidence above; the frontier would lie precisely where the consumer keeps its planning.
- **A second, project-shaped frontier vocabulary** (rejected) — the classification rule is the engine's one seam; the adapter maps facts, the engine never grows lookalike ladders.
- **Sight-only realization (reads transitive, writes refuse)** (rejected) — the write half is where the misplaced-block error class dies, and every write has a real native target; asymmetry bought nothing.
- **`assignProjectToGoal` as a separate verb** (rejected) — a second surface for the same semantic; the member kind is the binding's fact, not the verb's.
- **Cut pass files no members under initiative** (rejected by the consumer's own cost model) — everything but the initiative hand-made, recurring at every grill's follow-up filing; and the bare-invariant burden the option assumed does not exist for projects.
- **Team-scoped `listGoals` under initiative** (rejected) — hides cross-team finish lines silently; the honest scope is the container's own.

## Consequences

- CONTEXT.md **Goal** and **Frontier** amended: members are the container's direct native members; one vocabulary at every member granularity (this PR).
- #573 sharpens to the engine realization (contract generalization `issueId`→`memberId`, `createGoalMember` with the `blockedBy` arm, the Linear initiative realization, fake substrate, conformance — barrel and guard extensions ride the same diff). The goal-*skill*'s passes under initiative binding and the health write-mirror file as separate bare issues; `initiative` leaves `GoalBindingError: 'unrealized-container'` on Linear only when that engine issue lands.
- This ADR lands Coordinator-direct (ADR-0033: it closes no issue).

## Amendment 2026-08-16 — Decision 4's two pinned relation values were both wrong; a `String!` in this vendor's schema is not evidence of an unconstrained field

Decision 4 above says the project-relation `type` string "is typed free-form there, so its value is pinned at build time by one UI-created edge read back." The pinning happened; the read-back did not, and the values shipped inferred. A live write against a real Linear workspace on **2026-08-16** falsified **both** of them, so `LinearApi.addProjectBlockedBy` — and therefore `createGoalMember`'s `blockedBy` arm under an `initiative` binding — could not have succeeded against **any** workspace. Every attempt returned `Argument Validation Error`.

| Constant | Shipped as | Live API requires |
|---|---|---|
| `PROJECT_BLOCKS_RELATION_TYPE` | `'blocks'` | `'dependency'` — the only permitted value |
| `PROJECT_RELATION_ANCHOR_TYPE` | `'project'`, one value on both ends | `'start' \| 'end' \| 'milestone'` — `'project'` is not among them |

Verbatim from the rejection's `extensions.validationErrors`:

```
property: "type"               constraints: { isEnum: "type must be one of the following values: dependency" }
property: "anchorType"         constraints: { isEnum: "anchorType must be one of the following values: start, end, milestone" }
property: "relatedAnchorType"  constraints: { isEnum: "relatedAnchorType must be one of the following values: start, end, milestone" }
```

**Why the original read could not have caught it — this, not the corrected strings, is what the amendment is for.** Linear validates these fields as **enums one layer behind GraphQL**: a class-validator `isEnum` constraint that surfaces only inside a rejection's `extensions.validationErrors` and appears nowhere in the schema. Live introspection against the running API confirms `ProjectRelationCreateInput` still declares `type: String!`, `anchorType: String!`, `relatedAnchorType: String!`, with `ProjectRelation` returning `String` on the read side. The original read-stamp was therefore *honest and still wrong*: it correctly reported "typed as free `String`, so the schema pins their SHAPE and not their VALUES" and then treated the vendor's prose as the next-best evidence. But the schema here is not ambiguous, it is **structurally incapable of carrying the answer**, and the prose actively misled — `ProjectRelation.type` is documented "(e.g., blocks)", naming the one value the API refuses, because that example describes the relationship's semantics rather than its wire value. The generalisable rule, and the one worth more than the fix: **for this vendor a `String`-typed field is not evidence of an unconstrained field; only a live write answers, and the rejection payload names every offending property at once.**

**The anchor is asymmetric, so the correction is a shape change, not a string swap.** `PROJECT_RELATION_ANCHOR_TYPE` was a *single* exported constant used for both ends, because "anchored to the project itself" read as one symmetric value. The real model is a finish-to-start dependency: the blocker's `end` anchors to the blocked project's `start`. There is no correct value for a symmetric constant, so the export became a **frozen fragment keyed by its own wire field names** (`{ anchorType: 'end', relatedAnchorType: 'start' }`), spread wholesale into `ProjectRelationCreateInput`. Two named constants were considered and rejected: they are correct but leave a caller holding two interchangeable strings and a hand-written mapping onto two similarly-named fields, and a swapped pair is a *silent* defect — both are valid enum members in valid fields, so Linear records a backwards dependency without complaint. A rename in place was rejected outright: one value reachable for both ends is precisely what produced the original error. The fragment's literal-typed shape ships beside it as `ProjectRelationAnchorPair`, and both cross the root barrel.

*Correction (2026-08-16): this paragraph names the retired scalar (`PROJECT_RELATION_ANCHOR_TYPE`) and the fragment's TYPE (`ProjectRelationAnchorPair`) but never spells the live VALUE export's own name. It ships as `PROJECT_RELATION_ANCHOR_PAIR` — see `linear-api.ts`. The paragraph above is untouched as the record of what the correction WAS; this line is here so a reader grepping for the current symbol does not land on a name that no longer exists.*

**What the same probe CONFIRMED, recorded here so it is not re-measured.** Nothing below the strings changed, and decision 4's direction logic is untouched: the values round-trip verbatim with `projectMilestone: null`; `projectId` = blocker / `relatedProjectId` = blocked is the correct assignment; the relation surfaces on the BLOCKED project's `inverseRelations` and never its `relations`, carrying the blocker as `node.project.id`; Linear's own `hasBlockingRelations`/`hasBlockedByRelations` filters agree with that direction; and uniqueness is enforced per (project pair, type), **not** per anchor pair — so the facet's find-before-create idempotence already has the right granularity.

**Consequences.**

- Decision 4's parenthetical "the relation `type` string is typed free-form there, so its value is pinned at build time by one UI-created edge read back" is **superseded by this amendment**: the values are measured, and the mechanism it proposed (read the schema, infer, confirm later) is the mechanism that failed.
- Blast radius was narrow and stayed narrow: only the `initiative`-bound `createGoalMember` `blockedBy` arm was affected. `assignToGoal`, `createGoalMember` without a dependency, the frontier, and every issue-direct binding were untouched, and no consumer had an initiative-bound goal yet.
- The spec pins moved from constants to **literals** on both the real and the fake path. The version that shipped wrote `type: PROJECT_BLOCKS_RELATION_TYPE` in its expectation — quoting the constant back to itself — and the in-memory fake stored an abstract edge holding no wire strings at all, so neither could disagree with the code. Both now spell the measured values, and the fake records the same `projectRelationCreate` input the real adapter sends.
- The goal station's own reference prose (`.claude/skills/goal/reference/goal-mechanics.md`) still carries the pre-falsification "pending first live run" stamp; correcting it belongs to the goal-station row, not the engine row that landed this amendment.

## Amendment 2026-08-16 (operator ruling) — one house lesson, not two: the trap reading stays operative, the read-stamp's hindsight nuance rides along as a dated footnote

The amendment above and the read-stamp on `PROJECT_BLOCKS_RELATION_TYPE` in `linear-api.ts` (the section headed "WHY `'blocks'` WAS PLAUSIBLE: THE ARM ASYMMETRY, AND THE RULE IT YIELDS") draw on the same vendor sentence — `ProjectRelation.type`'s doc string, "The type of dependency relationship from the project to the related project (e.g., blocks)" — and read it two different ways. This record reads it as a TRAP: the prose actively misled by documenting an example that named the one value the API refuses. The read-stamp reads it as RECOVERABLE IN HINDSIGHT: the sentence's own NOUN (`dependency`) was the correct value and only its EXAMPLE (`blocks`) was wrong, so — in the read-stamp's own words — "the correction was recoverable from the published schema after all."

Neither reading is factually wrong, and both stand exactly as written above and in `linear-api.ts` — this is a ruling on which one the house holds as the operative lesson, not a rewrite of either. A reader meeting both documents was meeting two competing lessons from one sentence; that split ends here.

**The trap reading stays the operative lesson.** The vendor's prose actively misled — an example naming the refused value sits in the very sentence that would have saved the guess — and only a LIVE measurement settles a vendor value for this API. A doc string read whole is corroboration at best, never proof, and "measuring still beats both" (the read-stamp's own closing line) remains the load-bearing half of both readings.

**The read-stamp's hindsight nuance survives, dated, as the qualification it is — not a competing lesson:** the sentence's own noun (`dependency`) was the correct value, and only its example (`blocks`) was wrong. That is worth carrying into how the NEXT doc string gets read (nouns over examples), and it is not license to skip the next live write.

This record and the read-stamp now point at each other by name: this amendment names the read-stamp's section header above, and that section in `linear-api.ts` carries a matching dated cross-reference to this amendment. A reader who lands on either document meets the same one house lesson with the same one dated nuance, never two.
