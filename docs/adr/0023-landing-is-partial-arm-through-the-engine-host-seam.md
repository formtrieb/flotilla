# Landing automation is partial-arm through the engine host seam — no `gh` on any host-write path

`wave-close --auto` (ADR-0005's opt-in mode) gets its concrete shape from the 2026-07-16 auto-merge grill, under three fixed inputs: `--auto` stays **opt-in with human-confirm as the default posture**, the audience is **OSS** (consumers we don't sit next to), and a **Bitbucket+Linear team-internal pilot** is a named near-term consumer. Four decisions: **(1) partial-arm** — the confirm arms the order-free rows, the overlapping tail keeps the advisory merge-order as the human playbook; **(2) preconditions are probed and displayed, never dictated**; **(3) every host write goes through the engine host seam** — `gh` leaves the landing *and*, staged, the creation path; **(4) arm-and-exit** — no watch mode; `done` reconciles on the next touch, with a host-side evidence probe closing the no-integration gap.

## Partial-arm: the Conflict-Map decides what arms

Per-row arming eligibility is mechanical: verdict `approve`, no `needs-attention` flag, an open PR. There is **no second risk gate at landing** — a `public-API-change` row already met its human STOP at verdict routing (the G3 guard, fired three times correctly in the first live run); re-gating at merge would double-ask the same human. Wave-level, the confirm (**one per wave**, tabular: PR · row · verdict · conflict prediction · repo posture) arms exactly the rows that appear in **no Conflict-Map pair**; overlapping rows are listed with the recomputed advisory order — the Ur-strength ordered-landing experience preserved, with the order-free head landing itself. Headless runs never self-confirm: `--auto` without a human requires an explicit pre-authorization flag.

Intra-wave file overlap remains a first-class wave shape (`wave-plan`/`wave-create` record it in the spine `## Conflict-Map`; workers run in parallel regardless — worktree isolation makes the *work* conflict-free, only the *landing* needs order). Partial-arm is what keeps that strength under automation instead of trading it away.

## Preconditions: probe + transparency, not policy

Two GitHub facts shape `--auto`: the repo setting **"Allow auto-merge" is off by default** (without it arming simply fails — a hard *functional* precondition), and **a PR with no pending required checks cannot be armed** (GitHub rejects enable-auto-merge on an already-clean PR; the only host action there is a direct merge). So the store-preflight (FOR-12's home) gains two probes: **allow-auto-merge** (FAIL with fix instruction when off) and **required-checks presence** (**report-only**). A no-CI repo keeps `--auto`: the confirm then states "no required checks — confirming means immediate merge", which is semantically honest — the human just gave exactly that click, backed by the Worker's verify run and the Reviewer's independent one. We deliberately do **not** hard-require CI: visibility over gatekeeping, the FOR-12 line — hard gates only where failure would be silent, and this failure is loud.

## The engine host seam carries every host write

`gh` leaves the landing path entirely — and, staged, the creation path too (amending ADR-0019's "gh is still used by skills for PR creation"). Reasons, all live-proven: gh's creds are sandbox-denied and its TLS stack fought both the keychain (`OSStatus -26276`, retro P-6) and the proxy MITM cert (w2-F4) on REST **and** GraphQL; the merge identity was already the ambient `GITHUB_TOKEN` (the FOR-12 preflight probes precisely "can this token merge"); and the permission classifier gets one narrow, auditable CLI verb instead of a broad `gh pr merge` bash rule.

Mechanism per PR, deterministic: **checks pending → GraphQL `enablePullRequestAutoMerge`** (REST has no arming endpoint; GraphQL-where-REST-is-weak is the ADR-0019 pattern, same `GitHubHttp` seam as the closing probe) — **already clean → REST merge** (`PUT …/pulls/N/merge`, the exact call that landed run 1). No `gh --auto` fallback semantics to reverse-engineer. CLI surface: **`host-pr create | arm | merge | status`** with `detect-host` routing and host-local implementations (GitHub rides `GitHubHttp`; host-pr's cross-host Basic-auth `HttpProbe` stays untouched — the ADR-0019 boundary holds). `host-pr create` finally exposes the library's find-before-create idempotency (the P8 leftover), and this verb surface is what the Bitbucket pilot implements an adapter against — new adapter, no new skills.

Token shape: classic PAT `repo` scope is the live-proven path; fine-grained needs Pull requests: RW + Contents: RW. Two build-slice spikes: fine-grained-PAT support for the arm mutation, and the exact error shape of arming an already-clean PR. Identity note: merges land as the PAT owner — a GitHub-App/bot identity for teams is M2 (parallel to the Linear bot-identity question).

## Arm-and-exit; evidence-hierarchy done-reconcile

`wave-close --auto` arms/merges, prints the summary, archives, exits — **no `--watch`** in M1. Watching is the babysitting the server-side design abolishes (ADR-0005 chose arming *because* it survives a dead Coordinator); re-running wave-close (idempotent, archived spines included) is the interactive substitute. Accepted, documented latency: an armed PR whose checks later fail flags only on the next wave-close/resume touch.

Done-reconcile gains a host-side evidence source, hierarchy: **tracker attachment > host PR state (`host-pr status`) > nothing**. On a no-integration workspace (Linear without the GitHub integration — and the Bitbucket pilot, where Linear has no native integration at all) `readClosing` can never report `merged`; `host-pr status` answers "is the PR for this branch merged?" mechanically, and `issue-store close <id> <prUrl>` fires the FOR-13 `doneState` fallback — replacing the "out-of-band confirmed merge" prose with a probe. This docks onto FOR-20's evidence-state honesty (`closed-unmerged` vs closed-without-PR-evidence) rather than duplicating it.

## Considered Options

- **Partial-arm through the engine seam, arm-and-exit** (chosen) — keeps both proven strengths: the order-free subset lands itself, the overlapping tail keeps the human merge-order playbook; deterministic arm-vs-merge; narrow classifier surface; survives a dead Coordinator.
- **Arm-all + fall-behind flags** (rejected — ADR-0005's literal sketch) — simplest, but knowingly converts *predicted* overlaps into `needs-attention` noise the Conflict-Map could have prevented.
- **Hard disjointness gate** (rejected) — `--auto` only for fully-disjoint waves forfeits the common mixed wave (3 disjoint + 1 overlapping row) for no safety gain: a blocked PR fails loud, not wrong.
- **`gh pr merge --auto` as the transport** (rejected) — sandbox-denied creds, keychain/proxy TLS failures (P-6, w2-F4), a broad bash allowlist rule, and undocumented clean-PR fallback semantics.
- **GitHub Merge Queue as the standard ordered-auto path** (rejected as standard) — free on public repos but **paid on private** (Team/Enterprise); a dependency would tax exactly the small-team consumers flotilla targets. Noted as a consumer-side option; the M2 **rebase-train is "the free merge queue"** — offering the queue's ordered-landing feature tracker-agnostically at zero cost is an OSS differentiator, not merely a fallback.
- **`--watch`** (rejected for M1) — possible M2 sugar if operations show the reconcile latency hurts.

## Consequences

- **Engine surface:** `GitHubApi`/`RealGitHubApi` gain arm/merge/PR-status methods (GraphQL mutation + REST merge on the existing `GitHubHttp` seam); new `host-pr` CLI verb group (`create|arm|merge|status`, detect-host-routed); store-preflight gains the allow-auto-merge and required-checks probes.
- **Build slices:** **(A)** engine landing verbs + probes + spikes → **(B)** `wave-close --auto` partial-arm phase (blockedBy A; Files overlap FOR-20/FOR-21 on `wave-close/**` — the conflict-map will serialize) → **(C)** PR-creation moves to `host-pr create` (blockedBy A; touches the Worker terminator brief in `wave-shared`/`wave-start`).
- **Amends [ADR-0005](0005-pr-route-protected-main-merge-terminality.md)** (the `auto` mode's shape is partial-arm; the transport is the engine seam — the server-side-completion property is retained) and **[ADR-0019](0019-real-githubapi-is-raw-fetch-rest-graphql-behind-a-github-local-seam.md)** (the creation-stays-`gh` consequence is superseded, staged).
- The confirm table is the human-confirm default made concrete; explicit pre-authorization is the only headless bypass.

## Amendment (2026-07-20 — W10-F1: posture probes move to the host seam)

The first live `--auto` run (retro `2026-07-20-evidence-polish-w10`, finding W10-F1) hit exactly the blind spot this ADR documented: on a `linear` store the store-preflight reports the landing-posture checks `not-applicable` — the tracker seam cannot reach the code host — and the arm outcome was the only ground truth. Grill-settled 2026-07-20, four decisions:

1. **`host-pr preflight` joins the landing verb group** (`create | arm | merge | status | preflight`): detect-host-routed, built from `$GITHUB_TOKEN`, **no `--config`** — identical on every store kind. It reuses the `GitHubApi` posture reads that already exist behind the seam (`GET /repos` → `allow_auto_merge`, required-status-checks against the default branch, merge-capability). The Bitbucket pilot inherits the probe through the same adapter interface.
2. **Single-owner move.** The three code-host checks (`pr-merge-token`, `allow-auto-merge`, `required-checks`) leave `cli-store preflight` entirely; the store-preflight keeps tracker facts only (`tracker-host-integration`, `state-catalog`) and its usage text points to the host verb. One fact, one owner — the printer/parser discipline (ADR-0016) applied to probes. This supersedes this ADR's original "store-preflight (FOR-12's home) gains two probes" placement; the probes themselves are unchanged, re-homed.
3. **The check-status union gains `unknown`** — "the token cannot see this setting" (GitHub hides `allow_auto_merge` below maintain/admin). `unknown` never blocks; its detail carries the manual-verify / permission fix instruction. External consumer tokens must never *need* admin — this is the `closed-unknown` lesson (ADR-0020, W4-era false alarms) applied at the settings layer: absence of evidence is not a finding. A **visible OFF grades by context**: required checks present → `fail` (arming is structurally impossible; the fix instruction stands) — none → `advisory` (a clean PR direct-merges today; relevant once CI arrives).
4. **Choreography.** `wave-setup` runs both preflights (store, then host) at onboarding, making the allow-auto-merge setting an explicit CI-repo precondition with fix instruction (GitHub's default is OFF). `wave-close --auto` phase 4b sources the confirm-table posture column from `host-pr preflight` on every store kind; on `unknown` the confirm says so honestly ("posture unknown — the arm outcome decides"). The probe stays advisory: **the arm outcome remains the ground truth** — a behind/recomputing race is not probeable (the arm-degradation slice covers that class).

## Amendment (2026-08-10 — the Bitbucket adapter lands, and `arm` is measured)

The Bitbucket+Linear pilot this ADR named in 2026-07-16 began adoption, ran a full three-row wave on the engine unchanged, and hit the one thing that was never built: the landing seam refused, host-side, before any Worker dispatched. The adapter now exists (`adapters/bitbucket/bitbucket-api.ts`, implementing `LandingHost` + `LandingPosture`). The ADR's own prediction held — **new adapter, no new skills**: the router, the arm intent, the exit codes and the JSON shape are the shipped ones, and the only skill text that changed is the sentence that said `github` was the only adapter.

**The measurement this ADR owed itself: Bitbucket Cloud has NO per-pull-request auto-merge arming call in its REST API.** The original decision deliberately declined to assume GitHub-shaped semantics here (GraphQL arm + REST merge is "the GitHub shape, not a host-neutral fact"), and the measurement came out against the arm. What Bitbucket has instead is a *merge check* — "Allow automatic merge when builds pass", enabled per destination branch under Repository settings → Branch restrictions — and it is armed by a **human clicking Merge in the pull-request UI** while a build is still running; Atlassian's own KB says "After clicking on the **Merge** option, Bitbucket will watch the build for you and merge it if the build passes".

Be precise about which half is absent, because the first draft of this amendment was not, and got it wrong. It claimed "neither the merge endpoint nor any sibling endpoint exposes it". **The SETTING is exposed** — `allow_auto_merge_when_builds_pass` is one of the eighteen members of the `branchrestriction` `kind` enum in Atlassian's own OpenAPI document (`developer.atlassian.com/cloud/bitbucket/swagger.v3.json`, read 2026-08-10), readable and writable through the very `/branch-restrictions` collection this adapter already calls for `require_passing_builds_to_merge`. What is absent is a request parameter on `POST …/pullrequests/{id}/merge`, or any sibling endpoint, that arms **this pull request** to land itself later. The load-bearing conclusion is unchanged and rests only on that second half: with no arming call, `enableAutoMerge` throws the typed `AutoMergeUnavailableError` and intent routing falls back. What the correction does change is the posture read, which now genuinely *reads* that restriction instead of hardcoding `off` on a false premise (the first draft issued zero requests and called it a measurement) — and reports `on` as "the UI affordance exists on the default branch", never as "flotilla can arm", because turning the setting on changes what a human can click and nothing about what the engine can call. Consequences, all of them things the interface already had a place for:

- `enableAutoMerge` throws `AutoMergeUnavailableError('not-allowed')` — the typed refusal this ADR's own build slice invented for GitHub's "Allow auto-merge is off". The reason is `not-allowed` and **not** `clean-status`, because the two route differently: `not-allowed` degrades to a direct merge only when nothing required is pending and **refuses** otherwise, which is exactly "arm must never merge past a check"; `clean-status` would merge unconditionally. So `--auto` on Bitbucket lands the ready rows and reports the rest `refused`, and that tail takes the advisory merge-order — the same partial-arm shape decision 1 chose, reached from the other direction.
- **`armed` is unreachable on this host**, so decision 4's arm-and-exit has nothing to defer: `--auto` is synchronous there. That is a narrowing of the reconcile-latency consequence, not a contradiction of it.
- Mergeability is **derived**, because Bitbucket's PR payload carries no `mergeable_state`. The derivation is Atlassian's own merge-check sentence implemented literally — "Minimum number of successful builds for the last commit with no failed builds and no in progress builds" — so ZERO reported builds against a required minimum reads `blocked`, not `clean`. That closes the 2026-07-30 check-attach latency window on this host at the mergeability layer, which is why the adapter deliberately does **not** implement the optional `CheckAttachReader`: Bitbucket states its requirement as a **count**, not as named contexts, so a required-vs-reported *name* comparison would have an empty `required` list and be vacuously "attached" — re-opening the very window it exists to close.

**The credential shape was the second measurement, and it moved.** This ADR's Bitbucket assumption dated from an era of app passwords (`username:app_password`). Atlassian deprecated them — no new ones since 2025-09-09, existing ones ceased to function on **2026-06-09**, removed **2026-07-28** — so that pairing is not a shape to build against, it is one that has already stopped working. The two live shapes are an **Atlassian API token over Basic auth, paired with the ATLASSIAN ACCOUNT EMAIL** (`--user '{atlassian_account_email}:{api_token}'`, scopes `read:repository:bitbucket` + `write:repository:bitbucket`), and a **repository/project/workspace access token over Bearer**. `BITBUCKET_TOKEN` goes through the ADR-0029 seam; `BITBUCKET_EMAIL` is an identifier and does not. `host-pr create` rides the shared cross-host Basic-auth `HttpProbe` — deliberately NOT widened, the ADR-0019 boundary — so it requires the email pair and refuses the Bearer-only setup loudly, naming the variable.

**Posture grading became host-aware.** A visible `off` on GitHub is a fixable setting and can be a hard `fail`. On Bitbucket the same word grades `advisory` whatever its value, because the thing it names is a different thing: ticking `allow_auto_merge_when_builds_pass` enables a UI affordance for a human, and no value of it gives the engine an arming call — so there is no misconfiguration for an operator to fix and a `fail` would be permanently red on a correctly-configured consumer, which is noise rather than a signal. This is decision 3's `unknown` doctrine ("absence of evidence is not a finding") extended one step: the absence of a *capability* is not a finding either. `unknown` keeps its real meaning on this host too — it is reserved for a read that actually failed, never used to paper over a value nobody looked up. The merge-capability half of the posture rides the **workspace-scoped** permissions endpoint (`/user/workspaces/{workspace}/permissions/repositories`, documented filter `q=repository.name="…"`) — its unscoped predecessor is vendor-deprecated in the same OpenAPI document — and a read with no user context (a repository/workspace access token) stays no-evidence, never a finding.

**A third measurement, recorded because the first draft of this amendment asserted its opposite: Bitbucket Cloud DOES rebase.** The `merge_strategy` enum on `pullrequest_merge_parameters` has six members — `merge_commit`, `squash`, `fast_forward`, `squash_fast_forward`, `rebase_fast_forward`, `rebase_merge` — and the merge-a-pull-request support page names the same six in UI spelling (both read 2026-08-10). The adapter still declines to map flotilla's `rebase`, but for the true reason: flotilla's `MergeMethod` vocabulary has **one** `rebase` where Bitbucket has **two** strategies with different resulting histories, so any mapping would pick the consumer's history shape for them on the one write that cannot be rehearsed before a live wave. Nothing automated is affected — `DEFAULT_MERGE_METHOD` is `squash` and no wave path passes a method — so the refusal reaches only an operator typing `--method rebase` by hand, who is told what the two strategies are and where to choose between them.

**Not executable from this repo (ADR-0030).** flotilla's own remote is GitHub and no Bitbucket credential is reachable here, so every path above is specced hermetically over the injectable seam and compared against Atlassian's documentation rather than a live run. The pilot's next wave is the live reading — the same stance `RealLinearApi`'s and `RealGitHubApi`'s own unproven arms record.

## Amendment (2026-08-15 — the credential-shape sentence's scope pair was incomplete)

The 2026-08-10 amendment above states the credential shape as an Atlassian API token over Basic auth, "scopes `read:repository:bitbucket` + `write:repository:bitbucket`". Re-measured against Atlassian's own Bitbucket Cloud REST API OpenAPI specification's per-operation `security` field (triage 2026-08-15): every pull-request call the landing verbs and `host-pr create` issue — list, get, create, update, merge, the whole `/repositories/{workspace}/{repo}/pullrequests` family — is gated on a separate `read:pullrequest:bitbucket` / `write:pullrequest:bitbucket` pair, not on the repository pair that sentence names. That sentence is corrected in place by this line, not rewritten above it: the credential shape (Basic auth, account email plus API token) still holds, but its scope set does not stop at the repository pair. This ADR is not the living authority for the Bitbucket scope set — `reference/setup-mechanics.md`'s "Bitbucket token permissions" section (`.claude/skills/wave-setup/reference/setup-mechanics.md#bitbucket-token-permissions`) is, re-measured there as the adapter's call surface and Atlassian's own spec are re-checked; defer to it over this paragraph's scope names.
