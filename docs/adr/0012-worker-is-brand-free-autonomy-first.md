# Worker is brand-free and autonomy-first; model tier resolves through config, not the tracker label

The `Worker` vocabulary is **autonomy-first and free of model-brand names**: `background · background-heavy · foreground · HITL-required`. The primary axis a Worker value encodes is **autonomy** (who must be in the loop) — `background` = fully-autonomous AFK · `foreground` = a human co-pilots in chat · `HITL-required` = no agent grabs it until a human acts. The secondary axis — **model tier** — is carried only as an abstract `-heavy` marker; the binding `heavy → <concrete model id>` lives in the skill/driver config, **never in the tracker label**. This replaces the Ur-seeded set (`background-sonnet · background-opus · foreground-opus · HITL-required`), which baked a volatile model brand into a durable, human-visible label.

## Why

The Ur's enum conflated two orthogonal dimensions in one string: a **stable** autonomy class and a **volatile** model tier. Two problems followed:

- **Model brand names rot in durable tracker labels.** A `worker/background-sonnet` label written onto a GitHub issue in June misleads the moment the model line-up turns (Opus 4.8 / Sonnet 4.6 / Haiku 4.5 already churn fast). `Risk` was deliberately *frozen* as a load-bearing key (ADR-0007) — a brand name is the opposite of freezable, yet it sat in the same class of label.
- **Asymmetry + combinatorial blowup.** `foreground-opus` names a model; `HITL-required` does not (correctly — none runs). A third tier (`haiku`) would force `background-haiku`, `foreground-haiku`, … The brand axis multiplies the autonomy axis for no planning benefit.

Splitting the brand out is cheap and safe because **the engine does not switch on `Worker` values** — ADR-0007 records `Worker` as the one *freely trimmable* enum (it drives no string-keyed engine behaviour; only `Risk` does). The interpretation lives entirely in the skills/driver, so changing the default vocabulary cannot silently no-op an engine gate.

This also resolves two adjacent muddles on the **autonomy** axis:

- **`HITL-required` is a legitimate, eligible wave candidate — not a PRD-like non-unit.** It is real wave work at a node in the dependency graph (it may block downstream AFK slices); the coordinator *must* see it to prompt the human in time. So it stays eligibility-stamped and surfaces in `wave-plan`, where the driver treats it as "not autonomously dispatchable — human gate" (the `needs-attention` bridge, ADR-0006). The PRD-eligibility-pollution that ADR-0011 removed does **not** apply here: a PRD is a *document*, an HITL slice is a *work step*. That document-vs-work-step cut is exactly the one ADR-0011 draws — keep it.
- **AFK means "implement unattended," not "implement *and land* unattended."** A `public-API-change` slice can be built by a fully-autonomous `background-heavy` worker; it simply cannot *land* without the merge-time approval STOP (ADR-0007's `public-api-approval-required` guard, which fires at the verdict phase, not at dispatch). Landing approval is an orthogonal, automatic wave gate — not a `Worker` attribute. Had AFK required "land unattended," `background-heavy` (whose whole purpose is the cross-feature / public-API risk classes) would be self-contradictory.

## Considered Options

- **Brand-free, autonomy-first vocabulary; tier→model in config** (chosen) — one `Worker` field (minimal contract change, fits "route from Risk"); the load-bearing routing key stays stable across model generations; the human-visible label stops asserting a model choice that later silently stops being true.
- **Keep the Ur's coupled enum as opaque profile ids** (rejected) — "`background-sonnet`" as just-a-profile-name is defensible only if the name is *not* a brand; the label is human-visible (CONTEXT: "human-visible"), so a brand-named profile id still lies to a human reader as models churn. The honest version of "opaque profile id" is precisely the brand-free set.
- **Split into two fields: `autonomy` + `model-tier`** (rejected) — cleaner axes, but a bigger contract change, two labels per issue, and it commits the *model tier* to planning time when it is better read as a dispatch-time decision the driver can resolve (and re-tune) from `-heavy` + current availability.
- **Drop the tier from the issue entirely (autonomy-only `Worker`)** (rejected) — loses the slicer's useful static signal "this risky slice wants the strong model"; `-heavy` keeps that signal without naming a brand.

## Consequences

- **Default vocabulary changes:** `header-parser`'s `DEFAULT_WAVE_SCHEMA.workerValues` becomes `['background', 'background-heavy', 'foreground', 'HITL-required']`. This is a **deliberate deviation from the Ur** (flotilla's own guidance is not to re-import Ur specifics); the set is config-governed precisely so flotilla's default may differ. ADR-0007's "canonical Worker set" line is updated to match.
- **`to-issues` routing table** maps `AFK + Risk∈{mechanical, isolated-refactor} → background`, `AFK + Risk∈{cross-feature-refactor, public-API-change} → background-heavy`, HITL → `foreground` / `HITL-required`. The skill's AFK definition is narrowed to "implement unattended," with an explicit note that `public-API-change` slices will meet a landing-approval STOP.
- **Tier→model binding** is a skill/driver config concern (P7 `wave-start`): `heavy → <today's strong model>`, default tier → standard model. The engine never sees a concrete model id.
- **Transparency / re-tuning:** the *actually-dispatched* model is recorded by the **driver** in the spine dispatch-log at dispatch time — **not** self-reported in the `WorkerReport` (a model asked for its own identity hallucinates it). This gives consumers the `background-heavy → <model> @ <time>` signal to re-tune the tier binding, while the issue label stays brand-free. (P7 `wave-start` / spine work item.)
- **No new "non-eligible issue" path is needed in `to-issues`:** the only thing it ever files is eligible wave work; documents go through ADR-0011's Document facet.

## Amendment 2026-09-16 — the composer's literal-id fallback is retired; the engine derives a tier, never a model

"The engine never sees a concrete model id" was stated in Consequences above and then contradicted, in the engine, by one line: `compose-driver.ts`'s `modelForRisk()` returned the string `'opus'` for `cross-feature-refactor` / `public-API-change` and `'sonnet'` otherwise, and the composer used that as a silent last-resort fallback for a row's `model`. Two brand names, frozen in engine source, in exactly the position this ADR exists to keep them out of. The shipped driver template carried the same two literals in its `ISSUES` placeholder comment. Both are retired. Four things this amendment records:

- **The literal-id fallback is gone.** No engine code maps a tier marker to a model id. There is no default, no "today's strong model" spelled anywhere in `tools/wave/`, and no place left for one to rot.
- **The composer only ECHOES the model the Coordinator recorded.** A row's `model` is filled from its `--row-meta` `model` override, else from the model recorded on its spine dispatch-log entry by `spine set-branch --model` — an opaque pass-through, byte-identical from the spine to the composed row. A row with neither is **refused at compose time**, before the script is written, with a message naming the row id, its Risk-derived tier, and the `spine set-branch --model` remedy.
- **Risk→tier stays engine-derivable, as an ABSTRACT marker.** `modelForRisk()` (the name is retained; it is the spelling the barrel-drift allowlist holds) now returns `heavy` for `cross-feature-refactor` / `public-API-change` and `standard` otherwise. That much *is* the engine's to know: `Risk` is the frozen, load-bearing routing key (ADR-0007) and `heavy` is the same `-heavy` axis the `Worker` vocabulary already carries. Only the tier→id half was never the engine's.
- **Formalising tier→model as a config key is DEFERRED, not done here.** The obvious next step — a `models: { heavy, standard }` block in `wave.config.json` that the composer reads when a row records nothing — is a follow-on with its own config-schema, setup-scaffold and docs surface. This change deliberately stops at the refusal: an honest STOP naming the remedy is strictly better than a fallback that guesses, and it is what makes the deferred config key an addition rather than a correction. *(Annotation 2026-09-21 — this bullet stands as written and its deferral has been LIFTED: the key it describes shipped as `models`, exactly the spelling and placement this bullet named, in the amendment directly below. Read the bullet as the record of why the key was postponed, not as the current state.)*

**Consumer-facing behaviour change, ruled minor with a heads-up.** A consumer that never recorded `--model` used to get a silent `opus`/`sonnet` fallback and now gets a compose-time refusal naming the row. `wave-start` step 5 has always written `spine set-branch --model` for every dispatched row, so the operated path is unaffected; a hand-built spine, or a consumer driving `compose-driver` directly, must now record the model it wants.

## Amendment 2026-09-21 — the deferred config key ships as `models`, and the last brand literal in the shipped driver goes with it

The amendment above deferred the tier→model config key and left one thing unfinished that its own headline forbade: the shipped driver's Scribe stage still carried a concrete model id as its `agent({ model })` argument — the last brand literal in `tools/wave/`, missed because that amendment's pin scanned only for the two literals it had retired. The Scribe is a fixed cheap stage rather than a Risk-derived tier, so retiring its literal needs a compose-time constant, which is the deferred key. Both land here. Five things this amendment records:

- **The key is `models`, top-level and optional** — `{ heavy?, standard?, scribe? }`, exactly the spelling and placement the deferral bullet named. Every key is a non-empty string the CONSUMER chooses; the engine validates the block's shape and never the ids, because it has no vocabulary for one and acquiring one is what this ADR forbids. An unknown key inside the block is a `config validate` warning, not a refusal (ADR-0035).
- **It is the THIRD and weakest rung of the row-model ladder.** `--row-meta`'s `model` first, then the model recorded on the row's dispatch-log entry by `spine set-branch --model`, then `models.<tier>`. A blank is not an answer at any rung. A row none of the three answers for is still refused at compose time, and the refusal now names `models.<tier>` beside the `set-branch` remedy — so an operator is not sent to record the same id on every wave for ever.
- **The Scribe stage binds `models.scribe`, else `models.standard`, else the row's own recorded model** — and never an omitted `model` key. That floor is the point: a stage dispatched without a `model` re-inherits whatever model is coordinating the session, per stage, which is the cost regression the ADR-0007 amendment of 2026-07-31 closed for the Reviewer. `models.standard` sits ahead of the row model deliberately: the Scribe writes one sidecar file from a payload it is handed, and a heavy row's expensive model is the last thing it should inherit.
- **`modelForRisk` is renamed `tierForRisk`.** It has answered with an abstract marker since the 2026-09-16 amendment; the old model-shaped spelling survived one wave only because the barrel-drift allowlist pinned it from outside that row's declared globs. It is read for two things, neither an id: naming the tier inside the refusal, and choosing which key of the consumer's own `models` block to read.
- **Minor with a heads-up, and the heads-up has one real edge.** A consumer that declares no `models` block composes exactly what 2.7.0 composed — with one exception, which is the Scribe stage: it used to run on a hard-coded cheap tier and now runs on the row's own recorded model unless `models.scribe` (or `models.standard`) says otherwise. A consumer that wants the Scribe on a cheap tier declares it. Implementer-visible: `composeDriverScript`'s input gains an OPTIONAL `scribeModel`, `ModelsConfig` is a new root-exported type, and the module-local `modelForRisk` is gone.
