## Convention 5 — the sidecar write path (verb-written, at agent-return)

**Enforced by:** engine refusal — `tools/wave/src/sidecar.ts` (validate-then-write, with the filename engine-computed so a caller cannot misname it).

Sidecars — the durable Worker-report / Reviewer-verdict records under `.flotilla/waves/<slug>/reports|verdicts/` — are the WAL the resume doctrine ("disk beats a non-landed spine flip", ADR-0002) stands on. **The invariant (ADR-0024): every sidecar comes into being through the engine write verb, at the moment its agent returns — never hand-formatted, never bundled after routing.** This is the P-1 live-gate fix: a Coordinator death used to leave zero sidecars because they were written last, in a batch, after the Workflow returned.

- **The write verbs own the format.** `write-report`/`write-verdict` are the printers paired with the `sidecar.ts` reader (the way `renderSpine` is paired with `readSpine`, ADR-0016). They **validate-then-write** — an invalid payload is refused (exit 1, nothing written), the filename is engine-computed (`<id>-<iter>.md`, the caller cannot misname it), the body is the fenced-json block the reader parses, the target dir is `mkdir -p`'d, and a same-iter re-write is last-writer-wins. Full flags + exit codes: [reference/routing-mechanics.md](./routing-mechanics.md).

  | Verb | Renders | Id handling |
  |---|---|---|
  | `write-report --report-file <json> --reports-dir <reportsDir> --id <id> --iter <n> [--expect-digest <digest>]` | `<reportsDir>/<id>-<iter>.md` (fenced `WorkerReport`) | `--id` must be a **bare id** (else exit 2); `report.issue` is **normalized** to it when decorated (exit 0 + `notice:`), refused when it names a different row (exit 1) |
  | `write-verdict --verdict-file <json> --verdicts-dir <verdictsDir> --id <id> --iter <n> [--expect-digest <digest>]` | `<verdictsDir>/<id>-<iter>.md` (fenced `ReviewerVerdict`) | `--id` must be a bare id (else exit 2); no payload cross-check (a verdict has no issue field — like the reader) |

- **The write verbs refuse a payload the Scribe did not copy faithfully.** Two gates, both write-only, so the `sidecar.ts` reader and the shared structural validators stay as permissive about a historical sidecar as before. (1) **A key the canonical schema does not declare** — top level, or inside a closed nested object (`filesChanged`, an `acVerification` row, `documentedFormComparison` and its `divergences`) — is refused, with or without the flag: exit 1, nothing written, the key named. (2) **`--expect-digest <digest>`** refuses a payload whose canonical digest (`tools/wave/src/canonical-json.ts`: keys sorted at every depth, FNV-1a 64-bit — key order never moves it, a reworded list element does) differs: exit 1, nothing written, both digests named. The digest is taken over the payload as read, before `report.issue` is normalized, so a faithful copy always matches. The driver renders every Scribe's write command with the digest of exactly the payload embedded in its brief, so a paraphrase fails loud, the Scribe returns not-ok, and the routing-time recovery below rewrites the sidecar from the in-band payload. Live cause: in one wave the Scribe-written sidecar disagreed with the returned payload in 4 of 8 rows (an undeclared `verifyOutput` key; reworded `judgmentCalls`, `reviewerFocusItems`, `acVerification`), and only the divergence repair caught them — a resume path has no in-band payload to repair from. **The Coordinator's own two write paths — the inline `n = 1` path and resume recovery — pass no `--expect-digest`, by design (Operator ruling 2026-09-27):** both write straight from the payload the Coordinator already holds, so no independent copy exists to check it against, and a digest computed there would be taken over the very file just written and could only agree with itself. Both stay covered by the flag-free unknown-key refusal.
- **The bare-id contract, and the failure mode it exists for.** A sidecar's filename id IS its lookup key — the reader matches `reportFor(<row id>)` literally, precisely *because* an id is opaque and must never be parsed (ADR-0001). A **decorated** id therefore produces a real, schema-valid file that resolves for no row at all: **present to an `ls`, absent to a resume.** That is worse than a missing sidecar, which at least fails the existence check honestly. Live occurrence (`2026-07-27-consumer-gaps`): three of six Workers filled `report.issue` decoratively (`#126`, and two full `#NNN — <title>` strings); the write verb refused, so the Scribe reached for the one argument it controlled and passed the decorated string as `--id` — producing `#118-1.md` and `#126-1.md`, two finished Workers that a resume would have reported as having produced no durable record. The third could not be worked around and was simply never written. The fix puts the two halves where each can be obeyed: **`--id` is fixed and validated** (never the caller's to vary — varying it is now the refusal, not the escape from one), and **the payload's `issue` is repaired**, because a refusal aimed at a value the caller does not control is a refusal it will route around. `tools/wave/src/sidecar.ts` owns the shape rule and the normalizer; `tools/wave/src/route-cli.ts` applies both at the boundary.
- **Who runs the verb — per path.** On the Workflow-driver path, two cheap **Scribe** `agent()` stages run the verb (`worker → scribe(report) → reviewer → scribe(verdict)`) so the record is durable seconds after each agent returns, before any Coordinator routing (workflow-driver.md). On the degenerate inline path (`n = 1`, or an inline Reviewer re-dispatch), the Coordinator is its own Scribe — same verb, run immediately at agent-return. The old bundled post-routing write is gone.
- **A Scribe failure never discards the tuple.** The driver's Scribe stage passes the report/verdict through regardless and logs loud; at routing, the Coordinator checks each sidecar's existence and writes a *missing* one through the same verb (the documented recovery path, not the default).
- **The routing-time recovery also catches a MISNAMED sidecar — the write verb reports it.** The existence probe — `route-tuple`'s `sidecar-check` step on the dispatch path, or the hand-run `[ -f <reportsDir>/<id>-<iter>.md ]` on a resume path — cannot distinguish the two cases: a misnamed file fails it exactly as a missing one does. That is fine, because both answers lead to the same action — re-running the write verb — and **the verb now sweeps its target dir on every successful write** and reports any sidecar filed under a non-bare id (`warning: … MISNAMED SIDECAR …`, naming the file, the row it actually holds, and the name it should have had). The recovery therefore no longer rewrites the correct file and walks silently past the leftover. The verb **never deletes** the leftover: a misnamed sidecar may hold the only copy of a report, and a durability verb does not destroy data to tidy a directory — confirm the correctly-named record carries the same content, then remove it by hand. On the Scribe path the same finding rides back on `SCRIBE_RESULT_SCHEMA`'s `notice` field and is `log()`ed by the driver. **Where the sweep runs — both recoveries, and that is the whole point of the sentence.** There are two routing-time recoveries, not one: on a **resume** path the recovery is the write verb itself; on the **dispatch** path it is `route-tuple`'s `sidecar-check` step, which renders through the same body renderer but writes with its own writer. For several wave-generations only the first of those swept, which made the sentence above true of the verb and false of the path a live wave actually takes. Both sweep now, on every successful write, over the one shared detector (`findMisnamedSidecars` in `tools/wave/src/sidecar.ts`, applying `bareIssueIdViolation`) — so the rule about what a misnamed name *is* keeps a single owner. `route-tuple` also carries the finding structurally, in its `sidecar-check` step detail (`misnamed`), because its output is a JSON result a Coordinator reads at routing and a stderr line alone would leave it out of the record. Neither path deletes.
- **The routing-time recovery also repairs a DIVERGENT sidecar (issue #977) — present, valid, and disagreeing with the payload `route-tuple` was handed.** A missing/corrupt sidecar is `recovered`; a present-but-disagreeing one is a distinct third case: `route-tuple`'s `sidecar-check` step compares the on-disk sidecar against the payload as the write path would persist it (validated, and for a report, reconciled to the bare row id) field by field, top-level. No disagreement → silent, the ordinary case a Reviewer-only re-write at the same iteration (last-writer-wins) always produces. A disagreement → **the passed payload wins** (Operator ruling): the sidecar is rewritten from it through the same renderer and writer `write-report`/`write-verdict` use, a `warning:` line names the row, iteration, kind and every differing top-level field (`missing`/`extra`/`different`), and routing proceeds from the repaired record. This is reported as **`repaired`** beside `recovered` in the `sidecar-check` step's detail (`route-tuple`'s JSON: `steps: [ { step, status, recovered?, repaired?, ... } ] }`) — every disposition carries it, because the sidecar step runs before routing decides anything. One asymmetry: a payload that is itself unreadable or invalid, against a present valid sidecar, repairs nothing and leaves the sidecar standing — a record already on disk is never replaced by something the recovery itself would have refused to write in the first place.
- **`SCRIBE_RESULT_SCHEMA` is driver-local — NOT one of the drift-pinned copies.** The Scribe's `{ ok, path, error?, notice? }` return shape lives only in the Workflow driver; no engine const corresponds to it, so `skill-schema-drift.spec.ts` does not pin it and must not be extended to. Only `WORKER_REPORT_SCHEMA` / `REVIEWER_VERDICT_SCHEMA` above are drift-pinned.
