## Convention 8 — secret-safe tool output (binds every role, the Coordinator included)

An agent's tool output is not ephemeral — it is the session transcript on disk, long-lived and read by humans and downstream agents alike. **No role in this pipeline echoes an environment variable's VALUE into that output — not even with fallback syntax like `${VAR:-no}` — dumps the whole environment, or reads a gitignored settings/secrets file.**

### Who this binds — the Coordinator too, not only the briefs it composes

Read that sentence literally: this is **not** a rule about brief text. It is a rule about **tool output**, and it binds **every role that produces tool output** — Worker, Reviewer, Scribe, **and the Coordinator**.

That distinction has cost two credentials. The clause enforcing this convention ships to a Worker as policy clause 5 of `workerBrief()` (`.claude/skills/wave-start/reference/workflow-driver.md`), and **the Coordinator composes that brief — it never receives one.** The Coordinator is the single role in the pipeline that reads no brief, so it is precisely the role a brief-shaped rule cannot reach. Twice it then ran, in its own shell, the exact command the clause it had just authored forbids.

The consequence is about **placement**, not only phrasing: the safe form has to sit where a role reads *while it is acting*, not only where it writes for someone else. The two auth-preflight steps a Coordinator actually executes therefore carry the form **inline** — `wave-start` step 4 (`.claude/skills/wave-start/SKILL.md`) and `wave-close` phase 2 (`.claude/skills/wave-close/reference/phase-2-auth-preflight.md`) — and neither of them merely points here for it. A pointer is not read at the moment someone types a check; that is the whole finding.

### The one sanctioned presence test

```bash
[ -n "$VAR" ] && echo set
```

Prints the literal string `set` (or nothing) — never the token, never the whole environment, never a file's contents. There is no second sanctioned form, and no "just for diagnostics" exemption.

### Isolated roles do not probe — the Coordinator's preflight already proved it

The sanctioned form above answers *how* to check presence. It does not follow that every role needs to *ask* the question in the first place. A dispatched **Worker or Reviewer runs worktree-isolated** (`isolation: 'worktree'`, `.claude/skills/wave-start/reference/workflow-driver.md`) and is never the role that establishes whether a credential resolves — the **Coordinator's own value-free credential-probe preflight** (`wave-start` step 4, `wave-close` phase 2 — `{{wave-cli}} credential-probe --all`, exit-status only, described above) already proves resolvability **once, up front, before the flip** — before a single row is dispatched.

**The isolated-role rule: do not probe, sanctioned form or not.** A dispatched role re-running a presence test mid-slice is re-asking a question the Coordinator already answered on its behalf, from a vantage point — the interactive session, pre-dispatch — that is strictly the more authoritative one: the preflight STOPS the wave *before the flip* on a credential that fails to resolve, so a Worker or Reviewer that ever reaches the point of running its own task is already operating on a proven-resolvable credential. If resolution nonetheless fails **mid-slice** — a token expired or revoked in the window between preflight and dispatch — that surfaces as a **typed engine error from the call that actually needed it** (`host-pr create` exiting non-zero with a structured error). The role reports that as `blocked`; it does not pre-empt it with a presence check of its own. A probe run from inside the worktree, seconds before the real call, proves nothing about the instant the real call executes — it cannot out-run a credential that dies in that window — so it buys the role nothing the real call's own typed failure doesn't already tell it, at the cost of one more command for the guard below to reject.

**Why this is not merely tidiness — the presence test collides with a second guard.** The worktree-isolation guard — the "too complex to verify" refusal, mechanism B of [Convention 13](convention-13-one-bash-call-per-step.md)'s taxonomy — has rejected the one sanctioned presence form above (`[ -n "$VAR" ] && echo set`) when a worktree-isolated role ran it, **twice, live**: wave `2026-07-29-publish-prep-and-guards`, rows 216 and 226 (disclosed via `judgmentCalls`/`reviewerFocusItems`; row 226 additionally drew a Reviewer advisory on the same friction). Both rows record the guard refusing the sanctioned test outright as too complex to verify — each ran only after being re-wrapped in `bash -c`: "the sanctioned form being harder to run than a violation would be is exactly backwards." The friction was still an open item the very next day — `2026-07-30-ops-guards`'s close recorded it as "the sibling guard … is its own ticket on the board" (docs/retros/2026-07-30-beta1-double-wave.md, finding DW-F6) — and this section is that ticket.

**The fix removes the affordance rather than hardening the phrasing.** A `bash -c` wrapper is a workaround, not an answer — one more shape for the next occurrence to drift away from, the identical class of fix this convention's own leak history (below) already rejects in favor of removing the vector rather than re-wording it a third time. Under the rule above, a guard-passing presence-test *form* for an isolated role does not need to exist, because neither the Worker nor the Reviewer runs the check in the first place. **No legitimate isolated-role presence/probe check remains — stated here explicitly**, per this convention's own falsification discipline ([Convention 11](convention-11-prove-the-check-can-fail.md)): there is nothing left in the Worker or Reviewer brief for a falsification demonstration to apply to, because the check it would demonstrate no longer exists on either path. (The sanctioned form itself is unchanged and still correct for the role that actually asks the question — the Coordinator, never worktree-isolated, at the two preflight sites named above.) Worker and Reviewer briefs (`workflow-driver.md`'s `workerBrief()` policy clause 5, and `reviewerBrief()`'s workspace-setup section) both carry this isolated-role rule verbatim.

### The traps — why the unsafe forms do not look unsafe

- **`${VAR:-fallback}` substitutes the VALUE. It is not a presence test; it only reads like one.** The `:-` operator means *"use this default **when the variable is unset**"* — so on the branch that actually matters, the branch where the variable *is* set, the expansion evaluates to the variable's own contents. `echo "${GITHUB_TOKEN:-no}"` prints `no` only on a machine with no token; the instant there is one, it prints the token. Everything about the expression argues that it is safe: it is *shaped* as a yes/no question, it *names* a harmless literal, and the harmless literal is exactly the branch that never fires where the secret lives. Reading it does not reveal the bug — you have to know the operator.
  - **`${VAR:+yes}` (the `+` form) is genuinely value-free**, which is what makes the compound `${VAR:+yes}${VAR:-no}` the most convincing version of the trap: the first half really does print `yes`, so the output *starts* correct and looks like it worked, and the second half appends the live key right behind it. This is the form that fired live on 2026-07-27.
  - Prefer `[ -n "$VAR" ] && echo set` over *any* parameter-expansion form. Do not try to remember which of `:-` / `:+` / `:=` / `:?` are value-free — one sanctioned form, memorized, beats a rule you have to re-derive under time pressure.
- **Whole-environment dumps are not safe.** `printenv`, a bare `env`, a bare `set` — each prints every set variable, secrets included, regardless of which one you meant to check. `printenv GITHUB_TOKEN` is *worse*, not better: it targets the secret directly.
- **Reading a gitignored settings/secrets file is not safe.** `cat .claude/settings.local.json`, any `.env`-class file, or any other read-shaped command (`less`, `head`, `tail`, …) against one — "just to check a config precedent" is not an exemption; the file's contents land in tool output the instant it is read, live credentials included.
- **The constraint is on tool output generally, not on any enumerable command list.** A brief that never asks for `${VAR:-no}`, a `printenv`, or a `cat` of a gitignored settings file can still be defeated by any role free-styling a diagnostic mid-task. Tool output must never contain a secret — full stop — whether it originates from brief-scripted bash, an agent's improvised check, or a Coordinator's one-liner between two engine calls.

### Post-indirection — never execute the Lookup-Command (ADR-0029 amendment)

ADR-0029 changes what "the secret" is made of on an adopted consumer: a credential resolves through a per-project **Lookup-Command** (the `<VAR>_CMD` environment variable — `GITHUB_TOKEN_CMD`, `LINEAR_API_KEY_CMD`, `BITBUCKET_TOKEN_CMD`) before it falls back to the ambient variable. That command's stdout **is** the secret, so the doctrine above extends to it unchanged: **no role in this pipeline executes a configured `<VAR>_CMD` command outside the engine** — not to "see what it prints," not "just for diagnostics." The sanctioned alternative is the engine's value-free preflight probe — the same-shaped check as the presence test above, run by the auth preflight (`wave-start` step 4, `wave-close` phase 2) rather than typed by hand: it confirms the lookup resolves, exit status only, and never surfaces the output.

**The three names above are the engine's shipped credentials, and the probe's `--all` discovery list is now held to them by a check rather than by hand.** `BITBUCKET_TOKEN_CMD` was missing from this sentence for the whole of engine 1.3.0 — the same release in which `credential-probe --all` itself failed to discover the Bitbucket credential, so a consumer whose host credential was configured and reachable got `ok: true`, `probed: []`, exit 0 at both auth preflights: a **silent false all-clear**, the one failure mode a preflight cannot have. The list and the doc entry are both fixed; `tools/wave/src/credential-discovery-drift.spec.ts` is what keeps them fixed, by reading every production call site of the resolver and failing when one resolves a credential `--all` cannot discover. Note what did NOT change: the probe still selects on **environment presence alone** — no host detection, no store kind, no wave-config lookup — so a consumer that does not use a given host never fails a preflight over its credential. (`BITBUCKET_EMAIL` is deliberately *not* on this list: it is the Basic-auth username half, an identifier rather than a secret, and does not travel this seam at all.)

This is a structural gain, not one more clause to remember: on a consumer that has adopted the indirection, an environment dump has nothing to show — the pointer that lives in `process.env` is a command string, not a token — and seven of the eight live occurrences below were accidental forms that now lose their target entirely. The scope stays honest, per this convention's own doctrine: the deny entry anchors the **direct** command form only; wrapped forms — `echo $(…)`, a `sh -c` wrapper — are not reachable by a prefix matcher, and they are now family 4 of the **Echo-Guard** below, which is a speed bump on top of the anchor rather than a replacement for it.

### The structural anchor — settings-deny (Convention 8 hardening)

The first three live occurrences below each found a vector the previous occurrence's prose hardening hadn't named — the class does not depend on which specific command a role reaches for, so a fix that depends on having read and internalized a clause was never going to hold structurally. The fix that does not: tracked **`permissions.deny`** entries in `.claude/settings.json` blocking the `Read` tool — and, as far as the permission syntax can express it, Bash's read-shaped command forms (`cat`, `less`, `head`, `tail`, `more`) — against the gitignored secret-bearing files themselves (`.claude/settings.local.json`, `.env`-class files). This is the **structural backstop** for the *file-read* vector; the brief clause above (`workerBrief()`'s policy clause 5) stays as **defense-in-depth** on top of it. `wave-setup`'s tracked-settings scaffold (`.claude/skills/wave-setup/reference/setup-mechanics.md`) carries the identical deny entries for every consumer, so a fresh consumer repo inherits the anchor at bootstrap rather than only after its own live occurrence.

### The structural anchor — Lookup-Command deny (ADR-0029)

The direct-execution vector gets the same fix in kind. ADR-0029 has `wave-setup` scaffold a second tracked **`permissions.deny`** entry in `.claude/settings.json`, blocking the Bash tool against the exact `<VAR>_CMD` command prefix it scaffolds for this consumer — the engine's own `child_process` spawn inside an allowlisted CLI invocation is untouched (no conflict); the deny reaches only a role typing the command itself. This is the **structural backstop** for the *direct-command* vector, the same division of labor as the file-read anchor above: the deny entry is the backstop, the never-execute clause stays as **defense-in-depth** on top of it. `wave-setup`'s tracked-settings scaffold (`.claude/skills/wave-setup/reference/setup-mechanics.md`) is the channel — the same scaffold that writes the `<VAR>_CMD` entry and the matching keychain item also writes this deny entry, so every consumer inherits this anchor at setup time, the same way it already inherits the file-read anchor.

### Can a permission-level rule anchor the *echo* vector the same way? — assessed: no

Recorded so the question is not re-opened from scratch at the next occurrence. **The permission layer cannot express this vector.** Three independent reasons, any one of which is sufficient:

1. **Permissions adjudicate an invocation; this leak lives in the output.** A deny rule sees the command string *before* it runs and never sees stdout. The file-read vector is catchable at all only because the object of the leak — the path `.claude/settings.local.json` — appears *as an argument in the command*. In the echo vector the secret appears **only after expansion, in the output**; at decision time the command text contains a variable *name*, not a value. There is nothing for a rule to match on that is the secret.
2. **There is no anchor to key on, and no substring matcher to key with.** `Bash(...)` rules are **command-prefix** matchers (`Bash(cat .claude/settings.local.json:*)`), not regex or substring matchers over the command body. The dangerous element — `${VAR:-…}` — can sit anywhere in an arbitrary command, under any interpreter, at any position, and the variable *name* varies per consumer (`GITHUB_TOKEN`, `LINEAR_API_KEY`, whatever the next store adapter needs). There is no stable prefix that isolates it.
3. **Any approximation is over-broad and under-inclusive at the same time.** The nearest expressible rule, `Bash(echo:*)` in `deny`, would block every legitimate `echo` in every skill — and still not separate safe from unsafe, since a prefix matcher sees only the leading word: the sanctioned form starts with `[`, not `echo`, and an unsafe expansion is just as at home inside `printf`, `node -e`, a heredoc, a command substitution nested in another command, a value written to a file and read back, or a value pasted into a commit message. Denying the shape without denying the work is not achievable in this grammar.

**Both candidates from this assessment are now decided and built — neither is still open:**

- **Keep the credential out of the shell environment the Coordinator drives** → **decided as ADR-0029** and shipped: a credential resolves through a per-project **Lookup-Command**, so on an adopted consumer `process.env` carries a pointer, not a token, and "check whether the key is set" stops being a question worth typing. That is the genuinely structural one.
- **A `PreToolUse` hook** → **decided and built as the Echo-Guard**, below.

### The structural speed bump — the PreToolUse Echo-Guard (decided)

`tools/wave/hooks/echo-guard.cjs` is a zero-dependency CommonJS matcher over a Bash tool call's **command string**, run before the command executes. It exists because the assessment above is correct — a `Bash(...)` permission rule is a command-*prefix* matcher and the dangerous element can sit anywhere, under any interpreter — while a hook receives the full command text and can reject on a pattern. It was filed on the **seventh live occurrence** (2026-07-28, a bare `printenv`, after the rewrite this convention now carries had bound every role) — catalogued below alongside an eighth from later the same day, both recorded here only once the guard itself had landed. Per this convention's own doctrine, the response to a recurrence is removing the affordance, not another reminder.

**Failure mode: hard-block.** A match exits with the blocking code and a **teaching** rejection message on stderr — it names this convention and *both* sanctioned alternatives (the value-free presence test above, and the engine's value-free preflight probe for "can the credential be resolved?"). Not warn-and-confirm: AFK roles have no human to confirm, and for the Coordinator a dismissable warning is the very failure mode the evidence documents — a rule that has been read and then violated is not under-communicated. **The guard fails OPEN on its own crash** (malformed payload, unexpected exception → exit 0, command allowed). That is deliberate for a speed bump sitting behind real anchors: a guard that bricks every Bash call when its own parsing breaks costs more than the vector it closes. A crash is silent-permissive, never silent-denying.

**Four families, composed:**

1. **Credential-name expansion** — ANY `$`-expansion of a credential-shaped name (the configured credential names, derived from the `<VAR>_CMD` entries present at hook runtime, plus the suffix classes `_TOKEN` / `_KEY` / `_SECRET` / `_PAT` / `_PASSWORD` / `_CMD`) anywhere in the command, **except** inside the sanctioned presence-test template. Catches a bare `echo $GITHUB_TOKEN` as well as every fallback form of a known name.
2. **Value-substituting expansion** — `${NAME:-…}` / `${NAME:=…}` / `${NAME:?…}` for ANY letter-initial name (positional parameters excluded by construction). The catalogue's own lesson is that a rule closes only the vector it names, so this one denies the *form* independently of the *name* — it catches the fallback trap on names no suffix heuristic would have predicted.
3. **Whole-environment dumps** — every `printenv` invocation, with or without an argument; a bare `env`; an exactly-bare `set`. Position-aware about two literal spans a real invocation never sits in — a single-quoted string and a heredoc body — detailed in the false-positive budget below.
4. **Wrapped Lookup-Command** — any command containing a configured `<VAR>_CMD` **value** as a substring, read from the environment at hook runtime (config-driven, hence consumer-portable). This is what upgrades the wrapped forms — `echo $(…)`, a `sh -c` wrapper — from prefix-unreachable to caught, above the deny anchor that reaches only the direct form.

**False-positive budget, test-pinned** (`tools/wave/src/echo-guard.spec.ts`, one spec case each): the sanctioned presence test `[ -n "$VAR" ] && echo set`, the `env -u NAME cmd` runner form, and the allowlisted engine-CLI invocation shapes all pass untouched. Measured at grill time, the pipeline's operational surfaces contain zero legitimate value-substituting expansions — every fallback-form string in the skills is warning *prose*, not an executed command — so the composed set's real FP surface is near zero. One FP class is known and accepted: a command whose *argument* quotes an unsafe form as prose (`git commit -m "… ${VAR:-no} …"`) is blocked, because the matcher reads command text and cannot tell prose from an expansion the shell will perform. A benign FP costs one rephrase, guided by the rejection message.

**Family 3 is position-aware about two literal spans, closed after a same-day FP cluster** (2026-07-29-publish-prep-and-guards, rows 216/226, plus a Coordinator reproduction at close): a Reviewer's `grep -n` search *pattern* for the dump word — backtick-quoted, and quoted inside single quotes — was read as an invocation, and a `gh issue create` heredoc *body* that merely mentioned the word as the first word of a line was too. Neither is a real invocation: bash performs zero expansion inside single quotes, and a heredoc body is argument/stdin data for its reader, never a further sequence of commands. Family 3's head detection now blanks split-triggering characters found *inside* a single-quoted span (leaving double-quoted spans, where `$` and backticks are genuinely live, untouched — so an apostrophe like the one in `"don't …"` is never mistaken for a quote delimiter) and folds a heredoc's body lines into the line that opened it before scanning for a command head. Both carve-outs are scoped to family 3 alone — families 1, 2 and 4 still scan the unmodified command text — and neither weakens a real bare backtick command substitution, a real `$(…)` hidden inside a heredoc body, or any of the piped / command-head forms above, each pinned by its own spec case.

**Two more shapes further out landed 2026-07-30/31** (a double-quoted search-*pattern* alternation and its parenthesized variant; a quote nested inside a live `$(...)` substitution) — see `tools/wave/hooks/echo-guard.cjs`'s own module docstring for the full mechanism, since this doc stays a narrative summary rather than a second copy of the carve-out logic.

**A Scribe sidecar write was hard-blocked on a shape none of the above covers (2026-07-31, issue #347) — not a leak, a false positive, and the recorded diagnosis for it did not reproduce.** Wave `2026-07-31-tier-guidance-and-guards`, disclosure 326.1: a Scribe persisting row 326's own `ReviewerVerdict` — a verdict *about* the quote-nesting fix immediately above, whose evidence text necessarily *quotes* that fix's own guarded examples (`$(printenv)`, `` `printenv` ``) as prose — was blocked twice, byte-identical, via the Scribe brief's prescribed `cat > "<path>" <<'EOF' … EOF` sidecar-write form. Reproducing from the archived verdict sidecar's byte-exact payload (not the Scribe's own, unconfirmed, self-diagnosis — two synthetic reproductions of *that* diagnosis at triage both passed the guard, since both shapes were already carved out above) found the real trigger and a genuine bug, not merely an unbudgeted FP: `neutralizeHeredocBodies()`'s own prior docstring claimed real bash evaluates an embedded `$(…)` inside a heredoc body "regardless of whether the delimiter itself is quoted" — empirically false (verified against real bash: `cat <<'EOF'` prints an embedded `$(echo …)` as literal source text; only the unquoted `cat <<EOF` genuinely runs it, the same rule that makes a single-quoted *string* inert). A heredoc opened with a **quoted** delimiter — the Scribe brief's own prescribed form, chosen precisely so a Scribe never accidentally executes anything while writing a JSON payload — is therefore as inert to family 3 as a single-quoted span always was; only an **unquoted** delimiter still leaves an embedded `$(…)` genuinely reachable, and stays caught. Two prior spec cases had pinned the old, incorrect claim as a regression test; both are corrected in place rather than left alongside a newer, contradicting one.

**The honest scope survives the decision — this is a speed bump, not an anchor.** It is a *text* matcher over the command, so `V=GITHUB_TOKEN; echo "${!V}"` walks straight past it, and so does any deliberate string assembly. That bypass is pinned as its own passing spec case rather than papered over. **Passing the guard is not evidence that a command is safe.** Two vectors are deliberately not the guard's at all: reading a gitignored settings/secrets file (the settings-deny anchor owns it) and the *direct* Lookup-Command invocation (the ADR-0029 deny entry owns it). The guard is worth having precisely because it fires without anyone remembering the rule; it is worth not overselling.

**Distribution — stage 1 was flotilla-local and operator-applied; stage 2's gate is MET.** `.claude/settings.json` is agent-write-denied, so the `hooks` block that wires the script to the Bash tool started as a **ready-to-paste operator step**, documented in the script's own header, never silently pre-applied by an agent — an agent-side settings edit here is a defect, not a convenience. **Stage 2 was gated on one real flotilla wave surviving with no false-positive incident — the FOR-81 / ADR-0029 live-gate pattern, dogfood first, scaffold second — and that gate is now met:** wave `2026-07-29-conventions-wiring` ran 12 agents (3 Workers, 3 Reviewers, 6 Scribes) across 374 tool calls with **zero Echo-Guard rejections and zero false positives**, including two rows editing documentation that quotes the unsafe forms as prose — the one false-positive class this convention names and budgets for above. `wave-setup`'s tracked-settings scaffold (`.claude/skills/wave-setup/reference/setup-mechanics.md`, "Echo-Guard hook scaffold") now carries the identical hooks block plus a script copy for *every* consumer, unconditionally, on the same footing as the deny anchors — the next reader finds a landed decision here, not a pending one.

**Met the gate; did not close the vector.** Rolling the hooks block out to every consumer is a distribution change, not a capability change — the guard scaffolded everywhere is the same text matcher over the command string described above, with the same honest scope: a speed bump, not an anchor, walked past by any deliberate string assembly, and blind to the two vectors that were never its own (the gitignored-file-read and the direct Lookup-Command invocation, both still owned by the `permissions.deny` anchors this same scaffold writes). Universal distribution widens *where* the speed bump sits; it does not change *what* it is.

### What the count is evidence about

**Eight occurrences in nine days is a fact about the mechanism, not about eight operators.**

Six came from agents that had the clause in front of them. Two came from the role that never receives one. One reproduced, word for word, a command the clause names verbatim. Read as an operator problem, that reads as eight lapses of attention and argues for a firmer reminder. Read as a mechanism problem — which is what the distribution actually shows — it says something narrower and more useful: **a rule that has been read and then violated is not under-communicated, and a rule its author is not subject to is not a rule at their desk at all.** Prose hardening has a measurable track record here: each of the first three clauses closed the one vector it named and nothing else, and the fourth through eighth occurrences needed no new vector to get past all three.

So the response to a recurrence in this class is **not** another clause, and **not** a sharper warning. It is one of: move the safe form to where the role that will need it *reads while acting* (what this convention now does for the Coordinator), or remove the affordance entirely (the deny anchor, for the file-read vector; the two decisions above — ADR-0029's Lookup-Command indirection and the Echo-Guard — for the echo vector). A seventh reminder predicts a seventh occurrence — that is the only prediction the evidence supports, and the seventh occurrence duly arrived, which is why the guard exists rather than a seventh clause.
