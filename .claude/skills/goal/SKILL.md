# goal

A **Goal** is a named finish line: a set of **direct members** living in **one container on your tracker** — a GitHub Milestone, a Linear Project, a Linear Initiative, or a file on the local markdown store — plus its **Frontier**, the derived remainder of members that are not finished yet. **The member kind follows the container, never your choice at call time**: an issue under a Milestone, a Project, or the markdown goal file; a **project** under a Linear Initiative, because an initiative holds projects, not issues. This station is the fourth planning station, beside `triage`, `to-prd` and `to-issues`, and it runs in three passes:

| Pass | Writes? | What it does |
|---|---|---|
| **cut** | yes | mints the container and files its opening frontier as **bare** direct members — title, prose, provenance line — with the dependencies you already know drawn between them, natively, at mint |
| **curation** | yes | joins a direct member to the goal, naming its kind as it does, including the handoff when a placeholder outgrows itself and its slices join in its place |
| **status** | no | reports the five-state frontier — the native project state alongside it, under an initiative binding — and stops |

Your job is the **judgment** — what the finish line is, what its opening frontier contains, which issue belongs to it, and what the report means. The engine is the guardrail: it owns the container binding, the bare filing shape, and the frontier derivation, and it deliberately exposes no verb for dispatching or for declaring a goal finished. So this skill stays on the judgment; the CLI invocation detail lives in [reference/goal-mechanics.md](reference/goal-mechanics.md) and the report's own shape in [reference/frontier-report.md](reference/frontier-report.md) — reach for them once a pass is confirmed. You never write a tracker directly; every read and write goes through the engine CLI (`{{wave-cli}}`), which selects the configured store.

## When to Use

- A release, a launch, or any other finish line needs naming, and the first round of work it implies needs to exist before anyone can say what it is.
- An issue should join an existing finish line, or a placeholder has been sliced and its slices should join in its place.
- Someone asks "what is still open before we get there?"

Do **not** use this skill to make a member ready for a background agent — `triage` decides *whether* it is ready and `to-issues` writes the planning header it needs. Do not use it to capture a design as a PRD (`to-prd`) or to choose what runs next (`wave-plan`). And do not use it to run anything: this station dispatches nothing, ever.

## THE FLOTILLA BOUNDARY — sight, never permission

**Goal membership informs planning and authorizes nothing.** This is the one rule that makes the station safe to hand a planning agent, and every clause below is structural rather than a promise:

- **The station never stamps eligibility.** Cut files **bare** issues — no planning header, no readiness marker — so nothing it creates can be drawn into a wave on its own. Sharpening bare → ready stays where it lives: `triage`'s answerability test and `to-issues` decorate-mode. If you find yourself reaching for `issue-store annotate` here, **stop** — that is `to-issues`' job.
- **The station never dispatches.** The Goal facet has no dispatch verb and never will, so there is nothing here to reach for. An issue enters a wave because it is *eligible and passes the readiness gate* — never because it is in a Goal.
- **Downstream, membership is display only.** `wave-plan` may read the facet for a read-only goal panel or filter, exactly as it surfaces PRDs today. Every execution skill from `wave-create` onward is blind to the facet by design; do not teach one to read it.
- **The station never declares the finish line reached.** There is no close verb on the facet. Status reports that the frontier is empty; closing the container is **your** act in the tracker. The station owes the accounting, never the declaration — and because there is no durable marker to write, an agent has nowhere to record a release authorization for itself.

## Per-pass human yes

**Every writing pass previews its writes and takes an explicit confirm, and no pass inherits an earlier pass's approval.** A confirmed cut authorizes exactly the container and the members it previewed; a curation pass run five minutes later previews and asks again. Present the preview as the concrete list of writes — the container's name, each member's title, each dependency edge, each membership join — and wait for a yes before the first call. The status pass is read-only and needs no confirm.

**A cut and its first curation may fold into one preview under one confirm, when they are genuinely one operator decision made in the same sitting — this is sanctioned, not merely tolerated.** A mature-pool cut routinely needs both in the same breath: new placeholders filed, existing work joined. Asking twice for one decision would be ceremony, not extra safety. The fold carries one condition: the preview still lists both write sets **by name and kind** — which members are newly-minted placeholders (the cut) and which are joins of work that already existed (the curation) — so the single yes is knowingly a yes to two different kinds of write, never a blurred list that reads as one. This is not a standing exemption for curation in general: a curation pass run later, in a separate sitting, still previews and asks on its own. The fold applies only to a cut's own first curation, decided in the same breath as the cut itself.

## The container binding

Which native container a Goal is realized as is a **setup-time config fact**, `store.goal.container` in `wave.config.json` — never a choice made at call time and never one this skill makes for you. GitHub defaults to its Milestone, the only native container with direct issue membership; the markdown store defaults to its goal file; **Linear has no default at all** and refuses loudly, because live consumer conventions disagree about what a Linear project — or a Linear initiative — means. Linear realizes both roles it declares: `project` (direct issue members) and `initiative` (direct **project** members, minted under `store.team`, the consumer's config-bound team). A refusal names the config key and the roles the store ships — read it, fix the config, re-run. Never work around it by reaching for a tracker CLI. Full binding detail, the container-role table, and the refusal shapes: [reference/goal-mechanics.md](reference/goal-mechanics.md).

## Pass 1 — cut

**Existence first — for whatever is genuinely new.** At a cut you know *that* a workstream must exist long before anyone can say *what* it is, so a newly-drafted member is filed bare and sharpened later — bare **issues** under the three issue-direct bindings, bare **projects** under an initiative binding. A Linear project is *born* bare (a name, prose, a `backlog` status carry no eligibility semantics at all), so there is no bare invariant to protect there the way there is for an issue — but the same "existence first, sharpen later" judgment applies to both kinds.

**A cut over a mature pool is mostly curation, and that is the more common shape, not an edge case.** The greenfield picture above — every member freshly minted bare — describes a finish line cut over nothing. Cut a finish line over a pool that already has work in it, and most of what the finish line needs already exists: triaged, some of it dispatch-ready. The goal then acts as a **collecting lens** over that pool — most of the cut's job is naming the finish line and joining the work that already answers it (Pass 2, curation), and only the genuinely-unspecifiable remainder gets filed bare (this pass). **A release cut is the archetype of this shape**: the release itself is new, but most of what it ships was triaged and moving before anyone thought to name the release as a goal. Both shapes are the same pass and the same judgment — what belongs, what still needs writing up — so the steps below still apply; they just file fewer bare members when the pool is mature. Whether the cut's first curation may share the cut's own preview and confirm is answered in "Per-pass human yes" below.

1. **Name the finish line.** One title a stranger can read, plus a short prose description of what being finished means. Do not encode a date, a status, or a checklist in it — completion is a query over the members, not a sentence in the container.
2. **Draft the opening frontier.** One placeholder per workstream that must exist. Each carries a title, a paragraph of prose saying what the workstream is *for*, and a **provenance line** naming where the cut came from (the session, the design record, the conversation). Draw a dependency where you already know one — a placeholder may depend on another placeholder even while neither is specifiable yet. Under an initiative binding, a placeholder is a **project** rather than an issue: the same judgment (what workstream, what it's for) still applies, and the file below it becomes a project's description rather than an issue body.
3. **Preview and confirm.** Print the container, every member title, its kind (issue or project), every dependency edge, and stop. **Do not file anything until the person says yes.**
4. **File, blockers first.** Mint the container, then file each member — one engine-CLI call both files the bare member and joins it to the container, so there is no separate join step in this pass. Blocker-before-dependent, so a dependent can name a real id. Under an initiative binding each member files as a bare project under `store.team`, the config-bound team — no other team choice is made here, and moving the finished project to whichever team will run the work is a tracker-UI act afterward, outside this station. Capture every printed id — they are opaque; never reconstruct one from a title. Commands, input shapes, and the id-inversion step: [reference/goal-mechanics.md](reference/goal-mechanics.md).
5. **Report.** Name the goal, its members, and the next step for each: every one of them is a placeholder, and none of them can be picked up until it is sharpened — for an issue member, `triage` then `to-issues`; for a project member, sharpening means triaging and decorating the issues filed *inside* it, since the project itself carries no eligibility marker to sharpen.

> **The bare dependency is realized natively.** A dependency between two bare members becomes a real tracker relation — a GitHub issue dependency, a Linear issue relation, or (under an initiative binding) a Linear **project** relation — and writes no header line, so the members stay bare. The local markdown store cannot represent it and **refuses** rather than faking it; on that store, either file the member without the edge and record the dependency when it is sharpened, or file it decorated through `to-issues` in the first place.
>
> **The ship-member pattern — filing a release's own act as a member, with a dependency edge on every content member it waits on — is sanctioned.** A release finish line's own act (the version decision, the CHANGELOG, the publish, the post-publish closes) needs a home like any other workstream, and a "ship" member beside the content members it ships is a natural shape for a release-goal specifically. Draw a native dependency edge from the ship member to every content member it waits on — the same mechanism step 2 already uses between ordinary placeholders — and its `blocked` reading then names exactly what the release is waiting on: sharper, per-member sight than reading the goal's aggregate open remainder and inferring the same thing. **The duty this buys is real, and it falls on you, not on the station**: a member that joins the goal later by curation is invisible to the ship member until its edge is drawn by hand — `goal-create-member`'s native `blockedBy` only fires at mint time, and curation's `goal-assign` (Pass 2) never touches an edge, so nothing re-derives the ship member's blocker list as the pool grows. Record that duty in the ship member's own body, in its own prose — "redraw this edge whenever a member joins by curation" — so it outlives the person who filed it, and re-check the ship member's edges any time a curation pass adds a member this release should wait on.
>
> **The first live read-back happened on 2026-08-16, and both pinned values were wrong.** The confirmation this note used to be pending — draw one dependency on an initiative-bound goal against a live Linear workspace, then read the two constants back — has now happened. Neither pinned value held: `type: "blocks"` must be `"dependency"`, and `anchorType`/`relatedAnchorType: "project"` must be one of `start`/`end`/`milestone` rather than a whole-project anchor. The engine-side correction is tracked on its own ticket, outside this documentation pass, and had not landed as of this writing — **the read-back is done, the repair is not.** Until it lands, a native project-relation write under an initiative binding still sends the disproven values and Linear still rejects them; the engine still surfaces that rejection loudly, naming the minted member, so nothing is silently lost. Full detail: [reference/goal-mechanics.md](reference/goal-mechanics.md).

## Pass 2 — curation

**The frontier is deliberately editable, and every edit is a human act.**

- **Joining.** One call joins one direct member to one goal — an issue under the three issue-direct bindings, a **project** under an initiative binding. It is idempotent, and it touches membership only — never the claim marker, never the triage state, never eligibility, never open/closed. Any member may join: one you filed at the cut, one that already existed, a slice someone wrote last month. **Name the member's kind in the preview** — "the project '…'" or "the issue '…'" — so the confirm is never ambiguous about what is about to enter the container. Under an initiative binding, an issue-shaped id is refused before any write rather than silently joined: "add this issue to the goal" is the one confusion this kind check exists to catch, because an initiative holds the projects issues live in, never the issues themselves — if you meant an issue, name the project it lives in instead.
- **The slicing handoff.** When a bare member outgrows its placeholder, it becomes a PRD (`to-prd`) whose slices (`to-issues`) join the goal by curation — **the slices join, the PRD does not**. A PRD is consumed rather than finished, so it has no completion state to query and can never be a member; it belongs to the goal derivedly, through its slices. The superseded placeholder then closes — and closing it is your act in the tracker, or `triage`'s won't-fix route where that is the honest verdict. This station names the placeholder and hands it over; it does not close it. Under an initiative binding the superseded placeholder is a project, and its slices are still issues filed inside whichever project now carries the work.
- **Leaving.** There is no leave verb. A member leaves by being removed from the container in the tracker, which is where you do it; the station reads the result on the next status pass.
- **Preview and confirm, per pass.** List each join, each handoff, and what the frontier will look like afterwards. Then ask. A yes given to a cut is not a yes to a curation pass.

> **Pending first live run.** The join call tells an issue id from a project id by shape — an uppercase team key followed by a number (`EX-123`). No document states every Linear workspace's team keys are uppercase-only; a lowercase-keyed workspace would fail this shape check and fall through to a plainer, less-well-taught refusal rather than the typed one above. That direction is benign — the join still refuses, just with a less specific message — so this is a confirm-at-first-live-run note, not a blocker: check the actual team-key casing the first initiative-bound live pass encounters.

## Pass 3 — status

Read-only, free, and the pass most runs will be. Ask the engine for the frontier and render it; derive nothing yourself and write nothing at all.

Each member reads as exactly one of five states — one finished bookend and four open ones — whatever its kind:

| Reading | What it means | Who moves it |
|---|---|---|
| `done` | closed on the tracker | nobody; it is finished |
| `in-motion` | a wave has claimed it, or (for a project member) the project itself is natively `started`/`paused` | the wave that holds it, or whoever moved the project |
| `actionable` | ready, unblocked, unclaimed | a wave could pick it up now |
| `blocked` | waiting on a dependency nothing has resolved | whatever it waits on |
| `unready` | carries no eligibility marker at all — an issue with no planning header, or a project holding no eligible issue (an empty project reads this way too) | for an issue: `triage`, then `to-issues`. For a project: triage and decorate an issue inside it |

**Under an initiative binding, render the native project state beside the reading — that is what keeps `in-motion` honest.** The frontier's `in-motion` folds two different native facts into one word: a project a person moved to `started` or `paused`, or a project still `backlog`/`planned` that merely has a wave-claimed issue inside it. Say which, when you know it — the two carry different next steps for the reader (a project a person is actively driving, versus one only a wave row inside it is touching) — and never let one word imply a false precision the tracker itself doesn't show. `completed`/`canceled` collapse to `done`; `backlog`/`planned` on their own contribute nothing to the reading — the reading then rests on whatever is happening to the issues inside. Full mapping and worked rendering: [reference/frontier-report.md](reference/frontier-report.md).

Render the distribution, then name names: **who is `unready`** (and which of the two sharpening skills each one needs), **who is `blocked` and on what**, and who is moving. A blocker the store could not resolve counts as unresolved, never as clear — say so rather than presenting the member as free. Report shape, the operator translations for each reading, and the worked example: [reference/frontier-report.md](reference/frontier-report.md).

**Report an empty membership distinctly from completion.** A goal with zero members and a goal whose every member is done both derive `complete: true` — an empty remainder is empty either way — but they mean different things to the reader, so say which one you are looking at: "this goal has no members yet" is not "every member of this goal is finished." Only in the second case is the remaining step yours to take.

**On completion (every member done), report it and stop.** Say that every member is finished and that the remaining step is yours: **close the container in the tracker.** Do not close it, do not write a release marker, do not file a note beside it — there is deliberately nowhere to write one.

End every pass with the operator block: what happened → where it lives → what you do next.

## Common Mistakes

- **Stamping readiness at the cut.** A bare member has no planning header and no readiness marker on purpose — existence is recorded, wave-readiness is not implied. Decorating it here collapses two separate decisions into one and puts unsharpened work in front of a background agent.
- **Treating membership as candidacy.** A goal is a planning artifact; the readiness gate is the only thing that lets work into a wave. A member that is in the goal and not eligible stays out, and that is the design working.
- **Closing the container.** The station reports an empty frontier and stops. The declaration is a human act in the tracker; there is no verb here for it and adding one would hand an agent its own release authorization.
- **Making a PRD a member.** A PRD is consumed, never done, so it has no completion state to query. Its slices are the members; the PRD belongs to the goal only through them.
- **Riding an earlier approval.** Each writing pass previews and asks for itself. A cut approved this morning authorizes nothing this afternoon.
- **Filing members through a tracker CLI.** Every write goes through the engine CLI, which resolves credentials and selects the configured store. Reaching past it is the defect class the triage facet already retired once.
- **Spelling a dependency reference by hand.** Ids are opaque. Ask the engine to invert one; never split an id on a separator or rebuild it from a title or a filing hint.
- **Picking a container when the config does not name one.** A store that binds no default refuses on purpose. Set the key in the config; do not choose a container on the consumer's behalf.
- **Reading a goal panel as a wave plan.** Membership is a display column. It never orders, ranks, or qualifies candidates.
- **Passing the wrong id kind under an initiative binding.** A member id's kind follows the container, not your intent — an issue id where the binding wants a project (or the reverse) is a category error, not a typo. The engine refuses it before any write; naming the member's kind in your own preview is what stops you from hitting that refusal in the first place.
- **Letting a ship member's edges go stale.** A ship member's `blockedBy` list is drawn once — at mint, or by hand afterward — and nothing re-derives it: curation's `goal-assign` never touches an edge. A member joined by curation after the edges were drawn is invisible to the ship member's own blocked reading until someone redraws it by hand. State that duty in the ship member's own body; do not trust memory to carry it.

## Operator register (Convention 16)

**Everything you print for the person at this session is operator-directed output, and it holds one register.** Plain language, direct address ("du"/"you"), self-explaining. Translate every internal reference — a decision-record number, a convention number, a finding id, a wave slug, a retro path — into the one-line consequence it carries for them, instead of naming it. Introduce a domain term with a half-sentence the first time it appears in a session, then use it freely. End the run with an operator block: what happened → where it lives → what you do next. Operator-directed text follows the operator's own language; the artifacts you write — issues, PRs, decision records, spine entries — stay English. **Installed form is strict** — no internal token reaches the operator. **Source form**, flotilla's own repo, may append one compact reference pointer after the plain text. Full clause text, the operator mini-glossary, and the mistakes it closes: [wave-shared/reference/convention-16-operator-register.md](../wave-shared/reference/convention-16-operator-register.md), read as a file beside this skill's own directory — no skill invocation, no namespace to guess.
