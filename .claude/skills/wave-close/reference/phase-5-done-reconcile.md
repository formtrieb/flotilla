# Phase 5 — Done-reconcile + needs-attention for stuck rows

Probe each terminal row's closing state, then either **land it `done`** (a merged PR), **flag it** (a genuinely rejected PR / stuck row), or **report it** (no merge evidence either way).

**Read the outcome as a claim about evidence, not as a verdict.** The probe reports what it *found*, and the four outcomes are not equally alarming. Only `closed-unmerged` means "a PR was rejected" — `closed-unknown` means "nothing was found", which is not the same thing and must never be auto-flagged.

**Evidence hierarchy for a merge (ADR-0023): tracker attachment > host PR state > nothing.** `read-closing` (the tracker attachment) is the primary probe. When it **cannot see a merge** — `open` on a no-integration workspace where the tracker never attaches the PR, or `closed-unknown` where it found no PR either way — fall to the **host** for the evidence the tracker lacks: `{{wave-cli}} host-pr status --branch <branch>` answers "is the PR for this branch merged?" mechanically (`{ state: "open"|"merged"|"closed-unmerged"|"none", url? }`). Its `state` supplies the merge fact, and `issue-store close <id> <prUrl>` fires the FOR-13 `doneState` fallback on a `merged` answer — this **replaces the old out-of-band human-confirmation step** with a probe. Only when *both* the tracker and the host lack merge evidence is the answer "nothing" (report, leave `in-review`).

**Skip `parked` rows entirely — do not probe them** (ADR-0022). A parked row has no branch and no PR, so `read-closing` has nothing to find; its claim was already released at park time. Report it under the parked rubric below and move on.

**Skip every still-`planned` row too — it was HELD, never dispatched.** Same reason, one step earlier: no branch, no PR, no worktree, nothing for a probe to see. The row's `Worker` cell says which of the two holds it sat in, and the two report differently (rubrics below): a human-gated `Worker` means **awaiting-human**; an ordinary one means it was held on an intra-wave blocker. Read that cell — a probe run against either returns `closed-unknown` at best, and a `closed-unknown` that gets flagged is the exact false alarm this phase already exists to prevent.

**Landing a merged row is ONE verb: `close-row`.** Whenever the probe below (directly or via a host fallback) confirms a row **merged**, hand it to the engine and read the one result:

```bash
{{wave-cli}} close-row --spine <spine> --id <id>
# → { "ok": true, "verb": "close-row", "id": "<id>", "prUrl": "…/pull/8",
#     "prUrlSource": "row", "acked": [0, 2], "verdictIter": 2,
#     "closing": { "state": "merged" },
#     "steps": [ { "step": "spine-pr-log",    "status": "performed" },
#                { "step": "spine-closed-by", "status": "performed" },
#                { "step": "verdict-acked",   "status": "performed" },
#                { "step": "store-close",     "status": "performed" } ] }
```

In one call, in this order, it: upserts the row's `## PR-Log` line, upserts the row's `## Closed-by` line, derives the acked indexes from that row's FINAL Reviewer verdict, and only then records the close on the tracker with those indexes. Both spine writes happen **before** the tracker write, because the spine is the write-ahead log a resume reconstructs from (ADR-0002) — a kill in the middle leaves a spine that names the closing PR and a tracker that has not moved, which is the recoverable direction.

Four things to know about it, each of which used to be a step of yours:

- **The PR URL.** It reads the spine row's own PR cell; `--pr-url <url>` overrides it. Whichever is used must classify as a **real PR URL** — a pre-fill link, a `<PR-URL pending>` placeholder, a bare sha, free prose or an empty cell is **refused with exit 2 and nothing written**, to neither the spine nor the tracker. A refusal there means the row never got a real PR pinned; fix that first.
- **The AC tick (FOR-17 — the dead `--acked` wire, ADR-0004).** The verb derives the indexes from the **MAX-iter valid** verdict sidecar for the id, so after a changes-requested → re-dispatch cycle the answer always comes from the **latest** iteration, never a stale one. A missing or schema-invalid verdict sidecar is **not a failure** — `acked: []`, the `verdict-acked` step reports `skipped`, and the close still lands the row `done`. The tick is COSMETIC ONLY (ADR-0004): human-facing, never re-read as gate input, so an empty `acked` never blocks a close. Close-time, not verdict-time, is the deliberate moment to apply it: ticking at approve would overstate an AC if the PR later closed unmerged, and this step only runs once a merge is confirmed. Never parse `acVerification[]` by hand here — and never re-derive the indexes yourself; that derivation now lives inside the verb.
- **Re-running it is safe and is described, not hidden.** Every step reports `performed`, `performed-before` or `skipped`. A second run for the same id leaves exactly one `## PR-Log` row and exactly one `## Closed-by` line, and calls `close` again with the same arguments (`close` is itself an idempotent no-op-or-reconcile). Landing a **different** row afterwards leaves this row's two lines byte-identical — both writes are keyed by id, never a rewrite of the section.
- **It does not decide `merged`.** The evidence hierarchy above is yours: this verb lands a row whose merge you have already established, and does no probing of its own.

The verdicts sidecar dir it reads is `.flotilla/waves/<slug>/verdicts`, derived from the spine path (`--verdicts-dir` overrides it) — the same dir wave-start's Reviewer stage writes to (wave-shared Convention 5).

```bash
{{wave-cli}} issue-store read-closing <id>   # → { state: "open"|"merged"|"closed-unmerged"|"closed-unknown", prUrl? }

# merged → land the row with the one verb (above). Nothing to capture, nothing
# to parse, nothing to guard: the derivation and the close happen in one process.
{{wave-cli}} close-row --spine <spine> --id <id>

# closed-unmerged (a PR was FOUND and it did not merge) → flag recoverable-stop
{{wave-cli}} issue-store flag <id> \
  --kind recoverable-stop \
  --question "PR was closed without merging — reopen, re-dispatch, or abandon?" \
  --option reopen --option re-dispatch --option abandon

# closed-unknown → NO flag. Report it and ask the human. See the rubric below.
```

- **`merged` → land the row `done`** via the **done-reconcile**: `{{wave-cli}} close-row --spine <spine> --id <id>` (above). This is the operational trigger that reaches `done` for a merged row — the wire the live gate found missing (F1) — and it also writes the checklist tick the live gate found dead (FOR-17): the issue's AC checklist reads as done for exactly what the Reviewer verified, partial/not-met ACs stay unticked. The close underneath it is **idempotent no-op-or-reconcile**: on a native-integration tracker the merged PR already flipped the coarse projection, so it only records the closing PR + the cosmetic AC tick; a re-entrant wave-close re-run never double-posts. Do **not** re-implement close, and do not hand-assemble the derivation the verb performs. Then clear any stale flag: `{{wave-cli}} issue-store clear-flag <id>`.

  **Read the `closing` state the verb prints (#399).** After recording the facts it re-probes and reports the resulting `ClosingState` in its own result — and if that probe STILL reads `open`, it ALSO writes an unmistakable `STILL OPEN:` line to stderr. That is the rare-but-real gap where the merge evidence you just acted on did not translate into a native tracker close (a PR whose close phrase never linked, or a row satisfied by something other than a PR at all — an issue a release resolved is the worked example). The verb still exits `0` either way — recording the facts always succeeds — but exit `0` here is not "landed `done`" when this line fires. There is no further close verb for this case: the issue stays open until the native close happens, so finish it by hand in the tracker, the same direction decided in the grill that filed #399.
- **`closed-unmerged` → `recoverable-stop`** — the store **found a linked PR and it did not merge**: a genuinely rejected PR. It is NOT auto-moved back to `available`; doing so would let another wave re-grab the issue and redo deliberately-rejected work. The human dispositions it (reopen / re-dispatch from scratch / abandon).
- **`closed-unknown` → consult the host, then report only if still unproven** — the row is closed but `read-closing` found **no PR evidence either way**. This is *absence of evidence*, not evidence of rejection, so never flag on it alone (auto-flagging here raised `recoverable-stop` on three genuinely-merged rows in the wave that found it — the exact false alarm this outcome exists to prevent). Fall to the host (evidence hierarchy): `{{wave-cli}} host-pr status --branch <branch>`. `state: merged` → the PR did land, the tracker just never attached it → `{{wave-cli}} close-row --spine <spine> --id <id>` (above; the close it performs fires the FOR-13 fallback), done. `state: closed-unmerged` → the host proves a real rejection → flag `closed-unmerged` (below). `state: open`/`none` → still no merge evidence anywhere → report **`closed-unknown — closed, but no merged-PR evidence found; confirm before landing`**, naming the id, and let the human say what happened. **Never guess** between merged and rejected — the host answer decides, and only a genuinely silent host falls back to the human.
- **`open` → PR still in review; no flag** — the human merges it in the advisory order (or `--auto` armed it in phase 4b); a later re-run reconciles it. **No-integration workspace with `states.doneState` set (FOR-13):** the probe can **never** report `merged` (there is no tracker↔host integration to see the merge) — it stays `open` after the PR lands. Do **not** wait for an out-of-band human confirmation: consult the host directly — `{{wave-cli}} host-pr status --branch <branch>`. On `state: merged`, land the row with the SAME `{{wave-cli}} close-row --spine <spine> --id <id>` (above) — on a store with `states.doneState` the close it performs fires the FOR-13 fallback (mapped done-state transition + a loud advisory), landing the ticket even without the integration. On `state: open`/`none`, the PR genuinely has not merged; leave the row `in-review` for the next touch. `close-row` is idempotent end to end, so re-runs stay safe.
- **`failed`/`abandoned`** rows were already flagged by `wave-start`; do not double-flag unless `readClosing` also returns `closed-unmerged`.
- **`planned` + a human-gated `Worker` → report `awaiting-human`, never flag, never probe, never close.** The row was held in `wave-start`'s human lane every pass: no agent was ever dispatched for it, because none may be until a human acts (ADR-0012). Report it as **`awaiting-human — <id> held for <the human action>; never dispatched`**, naming the action a person can actually go and do. It is **not stuck** (nothing failed and nothing is in flight) and **not errored** (no verdict, no PR, no probe result exists to be wrong about) — those two readings are precisely what this rubric exists to prevent, and a `needs-attention` flag would assert both.

  **Its claim is still live, and that is the one thing to dispose of before you archive.** Unlike a `parked` row, an awaiting-human row is still `queued` — it was never flipped to `in-flight`, and nothing has released it. Archiving the wave with that claim standing strands the issue: it reads as claimed to every future `wave-plan`, with no live spine left to reconcile it against. So do not archive past one. Name the two exits and let the Coordinator pick:

  1. **The human acts now** — then this wave is not finished: re-enter `wave-start`, let the row dispatch, and come back to `wave-close`.
  2. **Park it** (ADR-0022) — `planned` is a legal entry into `parked`, so the row leaves this wave and its claim is released back to the pool for a future draw:

     ```bash
     {{wave-cli}} spine set-row-state "$SPINE" "$ID" parked   # fine state, FIRST — from planned
     {{wave-cli}} issue-store unclaim "$ID"                    # releases the claim → available
     ```

     Parking is never automatic and never something this phase does on the Coordinator's behalf — it is the disposition they choose when the human action is not coming in a useful timeframe.
- **`planned` + an ordinary `Worker` → report as held on an intra-wave blocker**, otherwise identical: never flag, never probe, never close, and the same claim-disposition question applies. Name the blocker it waited on.
- **`parked` → report, never flag** (ADR-0022). Report it as **`parked — released for re-planning`**, naming the issue id so the human can see what left the wave. Do **not** flag it, do **not** `close` it, do **not** `unclaim` it again (the claim was released at park time; re-running is harmless but pointless). The question a needs-attention flag would raise — "what should happen to this row?" — is already answered: it is coming back in a future wave, drawn fresh from the pool. Flagging it would be the exact false alarm the state exists to remove.

**Writing the awaiting-human line well.** Name the action, not a capability. The measured constraint behind the row that motivated this lane was the **Bash sandbox's write-deny on specific paths** — an agent's file-editing tool wrote the target fine; git plumbing under the sandbox could not unlink it. "Agents can't write there" is the over-broad version of that measurement and mis-classifies work agents can do unattended; it also gives the human nothing to act on. The full write-up is in [../../wave-start/reference/start-mechanics.md](../../wave-start/reference/start-mechanics.md) ("Why the human lane exists"). Report `awaiting-human — 12: rotate the PAT in the keychain`, never `awaiting-human — 12: agents can't write here`.

The flag is **orthogonal to the coarse rung** — the row stays at its current rung (`in-review` / `failed` / `abandoned`); `read().status` gives `needs-attention` precedence in the projection, but the underlying rung is unchanged. A `done` row (closed PR) reads `done` regardless of any lingering flag (closed wins over the flag).

## Common Mistakes

- **Flagging — or probing — a `parked` row.** `parked` is terminal *and silent* (ADR-0022): the claim is already released and the disposition is already decided. Do not `read-closing` it (there is no PR to find, so the probe can say nothing useful — it reads `closed-unknown` at best), do not flag it, do not `close` it. Report `parked — released for re-planning` and move on.
- **Reporting an awaiting-human row as stuck, errored, or `needs-attention`.** A human-gated row that sat `planned` all wave did not fail — it was held on purpose, every pass, because no agent may pick it up until a human acts. There is no verdict, no PR and no probe result behind it, so "stuck" and "errored" are both claims about evidence that does not exist. Report `awaiting-human`, name the action, and leave the flag alone: the question a flag would raise is already answered.
- **Probing a still-`planned` row at all.** No branch, no PR, no worktree — `read-closing` returns `closed-unknown` at best, and a `closed-unknown` that gets flagged is the same false alarm the `closed-unknown` rubric above exists to prevent. Read the `State` cell first; if it is `planned`, read the `Worker` cell to pick the rubric and stop there.
- **Archiving past an awaiting-human row and stranding its `queued` claim.** Unlike a parked row, its claim was never released — archive the wave and the issue reads as claimed to every future `wave-plan`, with no live spine left to reconcile against. Surface the two exits (the human acts and the wave re-enters `wave-start`, or the row is parked and unclaimed) and let the Coordinator choose before phase 6.
- **Leaving a `merged` row at `in-review` (only clearing its flag).** A merged PR must be landed `done` via `{{wave-cli}} close-row --spine <spine> --id <id>` — that is the done-reconcile (F1). Clearing a stale flag alone does not reach `done`, and in a no-integration `states.doneState` workspace nothing else ever will.
- **Re-implementing close, or re-assembling what `close-row` already does.** The close underneath is the existing `IssueStore.close()` verb — idempotent no-op-or-reconcile, and the FOR-13 fallback lives inside it. The AC-index derivation, the spine's `## PR-Log` row and its `## Closed-by` line all live inside `close-row`, in one order, in one process. Call the verb; never hand-roll a state transition, a "done" write, or a re-derivation of the indexes in the skill.
- **Re-deriving the AC indexes by hand (FOR-17 — the dead wire).** Every closed issue used to read "not done yet" on the tracker because no skill ever passed the indexes; `close-row` now derives them from the MAX-iter valid verdict sidecar and passes them itself. Never hand-parse `acVerification[]` here, never capture the derivation into a shell variable to feed a separate close, and never skip the tick because "it's optional" — there is nothing left for you to pass.
- **Reading an empty `acked` as a failure.** `acked: []` with the `verdict-acked` step reported `skipped` means there is no valid verdict sidecar for the row — nothing to tick. The close still landed. The tick is cosmetic (ADR-0004), so an empty `acked` is an answer, never a reason to stop or to re-run.
- **Deriving the AC indexes at verdict-in instead of at close.** The tick fires inside `close-row`, once a merge is confirmed — never earlier. An `approve` verdict whose PR later closes unmerged must never have ticked anything; ticking any earlier than the merged-row close would overstate what actually landed.
- **Re-reading the AC tick as gate input anywhere.** The ADR-0004 boundary holds unconditionally: the tick `close-row` writes is cosmetic/human-facing only. No gate, probe, or later wave may read it back — `acVerification[]` on the Reviewer verdict stays the sole ground truth.
- **Auto-moving `closed-unmerged` back to `available`.** A rejected PR re-grabbed by another wave redoes deliberately-rejected work. Flag it `recoverable-stop`; the human disposes.
- **Treating `closed-unknown` as a rejected PR.** They are different claims: `closed-unmerged` means a PR was found and it did not merge; `closed-unknown` means nothing was found. Never flag `closed-unknown` on the tracker probe alone — consult `host-pr status` first (the evidence hierarchy): the host's `merged` lands it, its `closed-unmerged` is the only evidence that justifies a flag, and only a silent host (`open`/`none`) falls back to the human. Flagging on the bare tracker probe raises `recoverable-stop` on rows that are simply done — the live defect this outcome exists to fix.
- **Skipping the `host-pr status` fallback in the done-reconcile.** On a no-integration workspace `read-closing` can never report `merged`, so a merged row sits `open` forever if you stop at the tracker probe. The evidence hierarchy (ADR-0023) is tracker attachment > host PR state > nothing: when the tracker can't see the merge, `host-pr status` supplies it and the close `close-row` performs fires the FOR-13 fallback. There is no out-of-band human-confirmation step any more.
- **Double-flagging `failed`/`abandoned` rows.** `wave-start` already flagged these. Only re-flag if `readClosing` also shows `closed-unmerged`.
- **Treating `needs-attention` as a rung.** It is orthogonal — the row keeps its rung; the flag is the human signal layered on top.
- **Reading `close-row`'s exit `0` as "landed `done`" without reading the `closing` state it printed (#399).** It re-probes after recording the facts and reports the `ClosingState` in its result; if that probe still reads `open`, it also writes a `STILL OPEN:` line to stderr. Exit `0` means the facts were recorded, not that the issue natively closed — do not skip past the printed state on the assumption that a nonzero exit is the only failure shape here. When it fires, there is no further close verb to reach for: the issue stays open until the native close happens, so close it by hand in the tracker.
